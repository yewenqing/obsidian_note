
讲义主要回答了一个核心问题：**当应用程序发起一个系统调用（如 `read()`）时，硬件与操作系统内核是如何安全地跨越“用户态—内核态”边界（User-Kernel Boundary），并在执行完特权操作后安全返回的？**

  

  

以下将这份讲义的内容系统拆解并为你详细解释：

  

### 一、 系统调用高层接口与概念（User's Perspective）

#### 1. 系统调用的本质与双重角色

- **为什么需要系统调用？**
    
      
    
      
    - CPU 具有 **特权模式（Kernel Mode）** 和 **非特权模式（User Mode）**。用户程序只能执行“安全”的指令子集，不能随意操作硬件（如直接关中断、访问任意内存/硬件寄存器）。
        
          
        
    - 系统调用是操作系统向应用程序提供的“抽象机器”接口，也是进入内核执行特权操作的**受控入口（Controlled Entry）**。
        
          
        
- **为什么不能用普通的函数跳转（`jal`/`call`）进入内核？**
    
      
    
      
    1. 普通函数调用**不能改变 CPU 的特权模式**（无法从 User 切换到 Kernel）。
        
          
        
    2. 普通函数调用**无法限制入口地址**（恶意程序可能会跳过内核的安全/权限检查直接执行敏感代码）。
        
          
        
- **常见的系统调用分类**：
    
      
    - **进程管理**：`fork()`、`execve()`、`waitpid()`、`exit()`（讲义给出了一个精简版 shell 的实现逻辑）。
        
          
        
    - **文件与目录 I/O**：`open()`、`close()`、`read()`、`write()`、`lseek()`、`mkdir()` 等。
        
          
        
    - 讲义还对比了 **UNIX 系统调用** 与 **Win32 API**（如 `fork`+`execve` 对应 `CreateProcess`）。
        
          
        

### 二、 跨越边界的通用机制（General Mechanism）

发起系统调用跨越用户/内核边界时，必须完成以下转换：

  

1. **CPU 模式切换**：从 User-mode 切换到 Kernel-mode（并在返回时切回）。
    
      
    
2. **栈指针（SP）切换**：保存当前的用户栈指针，切换/初始化为该线程的**内核栈（Kernel Stack）**。
    
      
    
3. **程序计数器（PC）切换**：保存当前用户的 PC，将 PC 强制跳到内核预设的**固定异常处理入口（Exception Vector）**。
    
      
    
4. **寄存器约定（Calling Convention）**：
    
      
    - 用户态将系统调用号、参数放置在约定寄存器中。
        
          
        
    - 内核处理完成后，将执行结果/错误码（`errno`）放回寄存器供用户态读取。
        
          
        

### 三、 硬件支持：MIPS R3000 协处理器 0（CP0）与异常机制

讲义以 MIPS R3000 架构为例，讲解硬件层面的异常（Exception）支持机制：

  

#### 1. 核心控制寄存器（位于 CP0）

- `c0_status`（状态寄存器）：包含中断使能（IE）和模式位（KU，0=Kernel, 1=User）。它保存了三级历史栈（**c**urrent 当前、**p**revious 之前、**o**ld 历史）：`KUc/IEc`, `KUp/IEp`, `KUo/IEo`。
    
      
    
- `c0_cause`（原因寄存器）：包含 `ExcCode`（异常代码，如 `Syscall=8`、外部中断 `Int=0` 等）。
    
      
    
- `c0_epc`（异常程序计数器）：保存触发异常时的指令地址，用于异常处理完成后返回。
    
      
    
- `c0_badvaddr`：保存触发内存缺页/地址错误的虚拟地址。
    
      
    

#### 2. 硬件自动处理流程（Hardware Exception Handling）

当发生系统调用（执行 `syscall` 指令）或中断时，**硬件自动执行以下原子操作**：

  

1. 将当前指令地址存入 `c0_epc`。
    
      
    
2. 将 `status` 寄存器的位向左推（把当前 `KUc/IEc` 存入 `KUp/IEp`），并将当前状态强制设为 **Kernel Mode（KUc=0）且关中断（IEc=0）**。
    
      
    
3. 将异常类型写入 `c0_cause` 的 `ExcCode`。
    
      
    
4. 将 PC 强制设置为通用异常入口向量地址（如 `0x80000080`）开始执行内核代码。
    
      
    

#### 3. 硬件返回机制（`rfe`）

- 内核处理完毕后，跳转回 EPC（`jr k1`）并在分支延迟槽中执行 `rfe`（Restore From Exception）指令。
    
      
    
- `rfe` 指令将 `status` 寄存器状态右移（将 `KUp/IEp` 弹回 `KUc/IEc`），**恢复发生异常前的模式与中断使能状态**。
    
      
    

### 四、 案例深度拆解：OS/161 `read()` 系统调用的完整全过程

讲义通过汇编代码逐行剖析了 `read(fd, buffer, nbytes)` 从用户态发起到内核处理并返回的 **完整 11 个步骤**：

  

```
[用户代码] 
  1. 将参数放入 a0, a1, a2 (以及栈)
  2. jal read (调用 C 库封装函数)
       ↓
[用户态 C 库 read 包装函数]
  3. 将系统调用号(5)装入 v0 (li v0, 5)
  4. j __syscall (跳至通用 syscall 入口)
       ↓
[__syscall 汇编函数]
  5. 执行 syscall 指令 —— 触发硬件异常陷入内核！
  ═════════════════════════════【用户态 / 内核态 边界】═════════════════════════════
[内核汇编异常入口: exception.S]
  6. 利用内核保留寄存器 k0, k1，保存旧 SP，切换到内核栈 (sp = curkstack)
  7. 在内核栈上分配 164 字节空间，将所有 37 个用户寄存器压栈保存为 struct trapframe
  8. 计算 trapframe 结构体首地址放入 a0 (addiu a0, sp, 16)
  9. jal mips_trap (调用内核 C 语言通用异常分发函数)
       ↓
[内核 C 语言处理: mips_trap() & sys_read()]
  10. 内核读取 tf->tf_v0 判断为 syscall，根据 a0-a3 获取参数并执行具体的 read 操作
  11. 处理完毕后修改 trapframe 中的返回值：
      - 成功：tf->tf_a3 = 0, tf->tf_v0 = 返回字节数
      - 失败：tf->tf_a3 = 1, tf->tf_v0 = errno 错误码
  12. 函数返回，进入 exception_return
       ↓
[内核汇编返回: exception_return]
  13. 从内核栈上依次恢复所有通用寄存器与 CP0 寄存器
  14. 恢复 SP 为用户栈，执行 jr k0 + rfe —— 切回用户态！
  ═════════════════════════════【用户态 / 内核态 边界】═════════════════════════════
[用户态 __syscall 恢复执行]
  15. 检查 a3：
      - 若 a3 == 0 (成功)：直接跳到返回 (jr ra)
      - 若 a3 != 0 (失败)：将 v0 写入全局变量 errno，并将 v0 改写为 -1，再返回
[用户程序]
  16. 获得返回值（成功为读取字节数，失败为 -1），继续向下执行
```

### 五、 核心要点归纳与复习总结

1. **Trapframe（陷阱帧）的作用**：它是用户态进程全部上下文在内核栈上的镜像。内核通过 `struct trapframe *` 指针，可以在 C 语言中像访问普通变量一样读取和修改用户态寄存器的值（包括修改传参、注入返回值和错误码）。
    
      
    
2. **MIPS 特殊保留寄存器 `$k0`, `$k1`**：编译器和用户程序不得使用这两个寄存器，专门留给内核在异常刚发生、尚未切换栈和保存寄存器时充当临时暂存变量。
    
      
    
3. **OS/161 返回约定**：
    
      
    - `a3 == 0` 表示成功，`v0` 返回操作结果。
        
          
        
    - `a3 != 0` 表示失败，`v0` 携带错误码（C 库负责将其转存到 `errno` 并给调用者返回 `-1`）。
