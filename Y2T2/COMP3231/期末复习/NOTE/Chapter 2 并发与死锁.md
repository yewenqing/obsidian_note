这两份讲义来自新南威尔士大学（UNSW）的操作系统课程（COMP3231/9201），主要系统地讲解了 **并发（Concurrency）与同步（Synchronisation）** 的问题、理论条件以及各种解决方案与同步原语（Primitives）。

  

### 第一份讲义：`w01b-concurrency.pdf` —— 并发问题与基础互斥机制

这份讲义侧重于**引出并发产生的问题（竞态条件）**，定义临界区（Critical Region）的解决条件，并探讨硬件指令（如 `Test-and-Set`）如何实现互斥锁。

  

#### 1. 并发的来源与竞态条件（Race Conditions）

- **并发的来源**：
    
      
    - 单进程内部的多线程并发。
        
          
        
    - 多个单线程进程之间的并发。
        
          
        
    - 即便是单线程进程，在内核态（Kernel Mode）下也存在并发（如中断、不同进程的系统调用交错执行）。
        
          
        
- **竞态条件（Race Condition）**：
    
      
    - 讲义给出了经典的 `count` 变量增减例子（`increment()` 和 `decrement()`）。
        
          
        
    - 因为读写不是原子操作（分为读取、修改、写回三步），两个线程交错执行会导致最终计算结果不可预测、丢失更新或产生逻辑错误。
        
          
        

#### 2. 临界区（Critical Region / Section）与正确同步的 4 大条件

- **定义**：访问共享资源（如共享变量、内存、文件等）的代码片段称为临界区。若未加协调地进入临界区，就会触发竞态条件。
    
      
    
- **解决临界区问题的 4 个必要条件**：
    
      
    1. **互斥（Mutual Exclusion）**：同一时刻不允许两个进程同时处于临界区内。
        
          
        
    2. **空闲让进 / 前进性（Progress）**：临界区外的进程不得阻塞其他试图进入临界区的进程。
        
          
        
    3. **有限等待 / 无饥饿（Non-Starvation）**：任何请求进入临界区的进程都不能无限期等待。
        
          
        
    4. **通用性（Generality）**：解决方案应具备普适性，不能仅依赖于特定 CPU 数量或特定执行速度假设。
        
          
        

#### 3. 互斥方案的尝试与硬件支持

- **软件尝试（如轮流机制 Taking Turns / 严格交替）**：
    
      
    - 缺点是**忙等待（Busy Waiting）**，且当一个进程在非临界区很慢或停止时，会阻塞另一个想进临界区的进程（违反 Progress 原则）。
        
          
        
- **关中断（Disabling Interrupts）**：
    
      
    - 进入临界区前关中断，离开后开中断。
        
          
        
    - 缺点：只能在内核态使用；会降低系统响应；**在多核（Multi-core）系统上无效**。
        
          
        
- **硬件原子指令（Test-and-Set / TSL）**：
    
      
    - 硬件保证“读旧值并写新值（置1）”是一个**不可分割的原子操作（Atomic）**。
        
          
        
    - 汇编层实现自旋锁（Spinlock）：通过 `TSL` 测试锁，未获取则循环自旋（Spin）。
        
          
        
    - 优点：可在用户态使用，适用于多核。
        
          
        
    - 缺点：**忙等待（Busy waiting/Spinning）白白消耗 CPU 时间**；多任务竞争时可能出现饥饿。
        
          
        
    - 现代处理器的变体：`Compare-and-Swap (CAS)`、`Load-Link/Store-Exclusive (LL/SC)`、`Atomic Arithmetic`（原子增减）等。
        
          
        

### 第二份讲义：`w02-sync.pdf` —— 高级同步原语与经典并发问题

这份讲义解决了忙等待问题（引入阻塞/唤醒），并深入讲解了三大同步原语：**信号量（Semaphores）**、**管程（Monitors）**、**条件变量（Condition Variables）**，以及操作系统中的典型并发难题。

  

#### 1. 消除忙等待：Sleep / Wakeup

- 当获取不到锁时，线程调用系统调用 `sleep()` 阻塞让出 CPU；持有锁的线程在释放时调用 `wakeup()` 唤醒等待者。
    
      
    
- **存在的问题（Lost Wakeup 问题）**：
    
      
    - 在朴素的生产者-消费者（Producer-Consumer / Bounded Buffer）模型中，若读取 `count` 状态与调用 `sleep()` 之间发生上下文切换，唤醒信号 `wakeup()` 可能先于 `sleep()` 发出并丢失，导致双方永久陷入沉睡。
        
          
        
    - **核心痛点**：“判断条件”与“执行睡眠”必须是**原子的**。
        
          
        

#### 2. 核心同步原语

##### ① 信号量（Semaphores）

- 由 Dijkstra 提出，内部维护一个整型计数器 `count` 和一个阻塞队列 `L`：
    
      
    - **`P()`（即 `wait` / `down`）**：尝试获取资源；若 `count <= 0` 则阻塞当前线程并入队休眠；否则 `count--`。
        
          
        
    - **`V()`（即 `signal` / `up`）**：释放资源；`count++`；如果有等待线程则唤醒一个。
        
          
        
- **特性**：`P` 与 `V` 操作本身是原子的，且唤醒信号会被累加记录（避免了 lost wakeup）。
    
      
    
- **互斥锁（Mutex）**：当信号量初始值设为 1 时，即退化为互斥锁。
    
      
    

##### ② 管程（Monitors）与条件变量（Condition Variables, CV）

- **管程（Monitor）**：
    
      
    - 是一种**语言级别的结构**（如 Java 的 `synchronized`），将共享数据和对其操作的过程封装起来。
        
          
        
    - 由编译器保证**同一时刻最多只有一个线程能进入管程执行**，大幅减少程序员犯错。
        
          
        
- **条件变量（Condition Variable, CV）**：
    
      
    - 用于在管程/互斥锁保护下等待某个特定“条件”成立。
        
          
        
    - **`cv_wait(cv, lock)`**：原子地**释放互斥锁并进入休眠**；被唤醒后会自动**重新获取互斥锁**。
        
          
        
    - **`cv_signal(cv, lock)`** / **`cv_broadcast`**：唤醒一个/全部等待该条件的线程（不会释放锁）。
        
          
        
    - **重要规则**：唤醒后必须使用 `while (condition)` 循环重新检查条件（避免虚假唤醒或条件再次被其他线程破坏）。
        
          
        

#### 3. 经典并发同步模型与 OS/161 实现

1. **生产者-消费者问题（Bounded Buffer Problem）**：
    
      
    - **信号量解法**：使用 `mutex=1` 保证临界区互斥，`empty=N` 跟踪空槽位，`full=0` 跟踪已用槽位。
        
          
        
    - **OS/161 条件变量解法**：使用一个 `lock` 保护缓冲区，配合 `cv_wait`/`cv_signal` 分别等待 `count == N` 和 `count == 0`。
        
          
        
2. **哲学家就餐问题（Dining Philosophers）**：
    
      
    - 模拟多进程竞争有限资源，防止因每个人都先拿一只筷子而导致**死锁（Deadlock）**。
        
          
        
    - 解法：引入状态数组（`THINKING`, `HUNGRY`, `EATING`），在互斥保护下仅当左右邻居均未就餐时才允许拿两只筷子并进餐。
        
          
        
3. **读者-写者问题（Readers and Writers）**：
    
      
    - 允许多个读者并发读取（只要没有写者）；
        
          
        
    - 写者必须拥有排他性独占访问权（排斥所有其他读者和写者）。
        
          
        
    - 通过记录读者计数 `rc`，第一个读者负责获取写锁 `down(&db)`，最后一个离开的读者负责释放 `up(&db)`。

## 死锁与活锁
  

### 一、 死锁与活锁的核心概念

- **死锁（Deadlock）定义**：一组进程中，每个进程都在等待一个只能由该组中另一个进程触发的事件（通常是释放被占用的互斥资源），导致所有进程都无法运行，也无法释放已持有的资源。
    
      
    
- **资源分类**：
    
      
    - **可抢占资源（Preemptable）**：可以从进程手中强行剥夺而不会产生不良后果（例如 CPU、内存页面）。
        
          
        
    - **不可抢占资源（Nonpreemptable）**：强行剥夺会导致进程运行失败或状态崩溃（例如打印机、磁带机、临界区互斥锁）。**死锁通常涉及不可抢占资源**。
        
          
        
- **活锁（Livelock）**：
    
      
    - 进程**没有被阻塞**，且在持续改变自身状态，但**永远无法向前推进（No progress）**。
        
          
        
    - **生活比喻**：两个人在狭窄走廊面对面相遇，同时向同一侧让路，反复同步调整方向，导致谁也过不去。
        
          
        
    - **代码场景**：使用 `try_lock()` 时，若获取失败则主动释放已持有的锁并等待固定时间重试；若两个线程完全同步重试，将陷入不断拿锁、放锁的活锁死循环。
        
          
        
- **饥饿（Starvation）**：
    
      
    - 资源虽然不断被释放，但调度算法（如短作业优先 SJF）总是优先分配给其他进程，导致某个长作业无限期等待（可通过先到先服务 FCFS 解决）。
        
          
        

### 二、 死锁产生的四个必要条件（Coffman 条件）

只有以下 4 个条件**同时成立**时，死锁才会发生：

  

|**必要条件**|**含义**|
|---|---|
|**1. 互斥（Mutual Exclusion）**|资源具有排他性，同一时刻只能被一个进程独占使用。|
|**2. 占有并等待（Hold and Wait）**|进程已持有了至少一个资源，同时又在申请新的资源。|
|**3. 不可抢占（Non-preemption）**|进程已获得的资源不能被强行剥夺，只能由进程主动释放。|
|**4. 循环等待（Circular Wait）**|存在一个进程链，每个进程都在等待下一个进程所持有的资源（形成环路）。|

### 三、 资源分配图与死锁建模（Directed Graphs）

讲义使用有向图对资源分配与请求进行建模：

  

- **节点**：圆形表示**进程**（$A, B, C\dots$），方形表示**资源**（$R, S, T\dots$）。
    
      
    
- **边**：
    
      
    - **资源 $\to$ 进程**（$R \to A$）：表示资源 $R$ 已分配给进程 $A$。
        
          
        
    - **进程 $\to$ 资源**（$B \to S$）：表示进程 $B$ 正在请求并等待资源 $S$。
        
          
        
- **死锁判断**：如果资源分配图中**存在有向环路（Cycle）**，且每个资源类型只有一个实例，则系统必然处于死锁状态。
    
      
    

### 四、 处理死锁的四大策略

#### 1. 鸵鸟算法（The Ostrich Algorithm / 忽略问题）

- **做法**：假装死锁从未发生。
    
      
    
- **合理性**：若死锁发生概率极低，而预防/解决死锁的代价过高（如严重牺牲系统并发性能），忽略它是工程实践中的实用权衡（UNIX 和 Windows 在某些复杂资源管理上采取此策略）。
    
      
    

#### 2. 死锁预防（Deadlock Prevention / 静态破坏必要条件）

通过制定严格的资源分配规则，**破坏四个必要条件之一**：

  

- **破坏互斥**：通常不可行，因为许多物理/逻辑资源本质上就不可共享（如打印机）。
    
      
    
- **破坏占有并等待**：要求进程在启动前**一次性申请所有所需资源**。缺点是难以预知全部资源，且资源利用率极低。
    
      
    
- **破坏不可抢占**：强行剥夺资源，这在打印机等设备上会导致任务直接失败，通常不可行。
    
      
    
- **破坏循环等待（最常用工程方案）**：**资源全局按序编号（Resource Ordering）**。规定所有进程必须严格按照递增顺序申请资源（如必须先申请资源 1，再申请资源 2），从数学上彻底杜绝形成环路的可能。
    
      
    

#### 3. 死锁检测与恢复（Detection & Recovery / 事后处理）

- **检测机制**：
    
      
    - **单实例资源**：周期性运行图遍历算法（如深度优先搜索），检测资源分配图中是否存在环路。
        
          
        
    - **多实例资源**：维护现有资源向量 $E$、可用资源向量 $A$、已分配矩阵 $C$ 和请求矩阵 $R$，通过类似拓扑排序的向量计算查找是否存在无法完成的死锁子集。
        
          
        
- **恢复手段**：最简单粗暴但有效的方法是**杀死死锁环路中的一个或多个进程**，强行回收资源让其他进程继续运行（优先选择可从头重新运行的进程）。
    
      
    

#### 4. 死锁避免（Deadlock Avoidance / 动态规避）

在资源分配前进行动态安全检查，若分配会导致系统进入**不安全状态（Unsafe State）**，则推迟分配。

  

- **安全状态（Safe State） vs 不安全状态（Unsafe State）**：
    
      
    - **安全状态**：存在至少一种进程执行序列（安全序列），使得即使所有进程突然提出其最大资源需求，每个进程也能依次顺利运行完毕。
        
          
        
    - **不安全状态**：不存在这样的安全序列。**注意：不安全状态不等于已经死锁，但存在演变为死锁的风险**。
        
          
        
- **银行家算法（Banker's Algorithm）**：
    
      
    - 模拟银行放贷：系统掌握每个进程的最大资源需求量（Credit Limit），每次分配前预演分配后的状态是否仍然“安全”，只有安全才真正放行。
        
          
        
    - **局限性**：实际操作系统中几乎无法在进程运行前准确预知其最大资源需求，且进程数量是动态变化的，因此很少在通用 OS 中使用。

```
            ┌── 概念定义: 互相等待释放资源、不可抢占资源、活锁与饥饿
            │
            ├── 四大必要条件: 互斥、占有且等待、不可抢占、循环等待 (Coffman)
死锁体系 ───┤
(Deadlock)  ├── 建模工具: 有向图 (资源/进程环路检测) 与 矩阵计算
            │
            └── 应对策略:
                 1. 鸵鸟策略 (直接忽略，平衡代价与正确性)
                 2. 预防 (破坏4条件，最实用: 资源全局有序编号)
                 3. 检测与恢复 (死锁检测算法 + 杀进程恢复)
                 4. 避免 (安全状态判定、银行家算法)
```
