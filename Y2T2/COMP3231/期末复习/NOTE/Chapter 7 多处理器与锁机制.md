

讲义主要围绕 **多处理器/多核硬件结构**、**操作系统架构演进（从每个 CPU 独立 OS 到对称多处理 SMP）**、以及 **多核并发下的硬件同步原语与缓存一致性（Cache Coherence）** 展开。

  

### 一、 为什么走向多核与多处理器？

1. **CPU 主频增长停滞（Power Wall / 功耗墙）**：
    
      
    - 单核 CPU 时钟频率的增长在 2000 年代中期（如奔腾 4 时代）遭遇瓶颈。
        
          
        
    - 摩尔定律仍在继续（晶体管数量持续翻倍），芯片设计转向在单一芯片上集成更多核心（Multi-core）。
        
          
        
2. **多处理器系统的优势与假设前提**：
    
      
    - **动机**：突破单 CPU 性能瓶颈，同时复用昂贵的硬件资源（如磁盘、内存、网络）。
        
          
        
    - **关键假设**：负载必须具有可并行性（Parallelisable），且不能严重受限于 I/O 或内存带宽（I/O-bound 或 Memory-bound）。
        
          
        
3. ==**阿姆达尔定律（Amdahl’s Law）**：==
    
      
    - ==加速比公式：$\text{Speedup} = \frac{1}{(1-P) + \frac{P}{N}}$（其中 $P$ 为可并行部分比例，$N$ 为处理器个数）。==
        
          
        
    - ==核心结论：**系统的加速上限由串行部分 $(1-P)$ 严格限制**。哪怕拥有无限个 CPU（$N \to \infty$），当串行部分占 $50\%$ 时，最大加速比也仅为 2 倍。==
        
          
        

### 二、 硬件架构分类与总线瓶颈

讲义重点分析了 **基于总线的一致内存访问（Bus-Based UMA, Uniform Memory Architecture）** 架构：

  

- **结构**：多个 CPU/Core 通过一条共享系统总线（Shared Bus）访问同一块全局共享内存（Shared Memory）。
    
      
    
- **UMA 特性**：所有处理器访问内存的速度大致相同。
    
      
    
- **局限与瓶颈**：随着 CPU 数量增加，**总线带宽（Bus Bandwidth）迅速成为系统瓶颈**。
    
      
    
- **多级缓存（Cache）与一致性（Cache Coherence）**：
    
      
    - 每个 CPU 拥有私有 Cache（L1/L2 等）以减少对内存总线的访问。
        
          
        
    - **缓存一致性问题**：当 CPU 1 写入某地址后，CPU 2 读取该地址时不能读到旧的私有缓存内容。
        
          
        
    - **硬件解决**：硬件自动处理一致性，写操作会向总线广播使其他 Cache 中的对应行失效（Invalidate）或更新，这同样会占用总线带宽。
        
          
        

### 三、 操作系统对多处理器的支持演进

当多处理器硬件出现后，OS 该如何架构？讲义展示了三种演进阶段：

  

#### 1. 方案一：每个 CPU 运行独立的 OS（Each CPU has its own OS）

- **做法**：静态切分物理内存，每个 CPU 独占一部分内存运行独立的操作系统副本，共享外设。
    
      
    
- **优点**：实现简单，无 CPU 间的内核并发问题，适合早期过渡（现代类比：云端的虚拟化/虚拟机）。
    
      
    
- **缺点**：
    
      
    - 负载不均衡：可能一个 CPU 忙到过载，其余 CPU 完全闲置。
        
          
        
    - 内存无法共享：可能一个 CPU 内存不足导致颠簸（Thrashing），而其他 CPU 仍有大量空闲内存，无法跨 OS 动态调配。
        
          
        

#### 2. 方案二：对称多处理 + 大内核锁（SMP with Big Kernel Lock）

- **SMP 定义**：单个 OS 内核在所有 CPU 上统一运行，动态调度所有任务并平衡资源。
    
      
    
- **大内核锁（BKL / Single Mutex）**：
    
      
    - 为了防止内核数据结构被并发破坏，用一把全局互斥锁把整个内核变成一个巨大的临界区。
        
          
        
    - 同一时刻**只有一个 CPU 能执行内核代码**。
        
          
        
- **瓶颈**：一旦内核态处理时间增加，BKL 迅速成为性能瓶颈，无法扩展到更多核心。
    
      
    

#### 3. 方案三：对称多处理 + 细粒度锁（Fine-Grained Subsystem Locking）

- **做法**：将内核拆分成独立的子系统（如调度器、虚拟内存、文件系统等），每个子系统使用独立的互斥锁。
    
      
    
- **挑战**：
    
      
    - 内核子系统之间存在复杂的交织依赖。
        
          
        
    - 当一个操作需要同时获取多个锁时，**极易引发死锁（Deadlock）**，必须设计严格的全局加锁顺序（Lock Ordering）。
        
          
        
    - 某个子系统的细粒度锁可能会成为新的竞争瓶颈（如后续案例中的虚存锁）。
        
          
        
- **Linux 的演进历史**：
    
      
    - Linux 2.0 (1996)：引入单一 BKL；
        
          
        
    - Linux 2.2 / 2.4：逐步剥离中断处理与部分子系统锁；
        
          
        
    - Linux 2.6：全面推行基于数据的细粒度锁，直到 2011 年（Linux 2.6.39）才彻底移除 BKL。
        
          
        

### 四、 真实案例分析：UNSW 1990 年代服务器扩展性惨痛教训

- **背景**：UNSW CSE 采购了一台 4 核心（后升至 6 核、8 核）的大型服务器带 80 台 X-Terminals。
    
      
    
- **现象**：平时测试正常，但在学生交作业的高并发期机器彻底卡死；供应商将 CPU 升级到 8 核后**性能毫无改善**。
    
      
    
- **解决**：最终用 3 台便宜的 2 核机器替代，性能大幅提升。
    
      
    
- **根本原因**（引自 1992 USENIX 论文）：
    
      
    - 当时的操作系统在**虚拟内存 HAT（硬件地址转换）层使用的是单线程粗粒度锁**。
        
          
        
    - 4~8 核机器在高负载下引发严重的锁竞争（Lock Contention），增加更多 CPU 只是让更多核心排队等待同一把虚存锁，导致锁持有者变慢、等待队列更长。
        
          
        
    - 2 核机器的锁竞争极低，因此多台 2 核小机器的表现反而远超一台 8 核大机器。
        
          
        

### 五、 多处理器同步与锁的实现（Hardware & Cache-Aware Locks）

在多核环境下，单核常用的“关中断（Disable Interrupts）”完全失效（无法阻止其他核心并行执行），必须依赖硬件原子指令。

  

#### 1. 朴素自旋锁：Test-and-Set (TSL)

- **代码**：`while (TSL(lock) == 1);`
    
      
    
      
    
- **硬件机制**：执行 TSL 指令时，硬件需要锁住总线/独占访问内存。
    
      
    
- **缺陷**：自旋等待的核心在循环中不断发起带有写意图的 TSL 操作，**持续占用总线并阻塞总线访问**，即使其他 CPU 没有竞争这把锁，其内存访问也会被严重拖慢。
    
      
    

#### 2. 优化自旋锁：Test-and-Test-and-Set (Read before TSL)

- **代码**：
    
      
    
    C
    
    ```
    start:
    while (lock == 1);       // 1. 先用普通读指令在本地 Cache 中自旋
    r = TSL(lock);          // 2. 看到锁变为 0 时，才真正发起 TSL 尝试抢锁
    if (r == 1) goto start;
    ```
    
      
    
- **原理与优势**：
    
      
    - 普通读操作使得锁变量以“只读共享（Read/Valid）”状态存在于所有等待 CPU 的私有 Cache 中。
        
          
        
    - 只要锁未释放，所有等待 CPU 仅在自己的本地 Cache 中轮询，**不会在总线上产生任何通信流量**。
        
          
        
- **遗留缺陷（释放风暴 / Invalidate Flurry）**：
    
      
    - 当持锁者释放锁（写 0）时，所有 CPU 的 Cache 行瞬间失效，所有等待 CPU 会**同时发起 TSL 争抢**，在释放瞬间引发剧烈的总线风暴与锁竞争，拖慢持锁者的执行速度。
        
          
        

#### 3. 更高级的锁设计（扩展内容）

- **Ticket Lock（排队号锁）**：类似银行叫号（`avail` 和 `curr`），每个 CPU 领一个号后自旋等待 `curr == ticket`；释放时仅 `curr++`，**只有下一号 CPU 会尝试执行**，消除了争抢风暴。
    
      
    
- **MCS / Queue Locks**：等待核心通过原子操作在内存中构建一个显式链表队列，每个 CPU 仅自旋在自己独占的节点变量上，释放锁时直接点对点唤醒下一节点，实现完全无总线争用的优雅传递。
    
      
    

### 六、 自旋锁（Spinlock）vs 阻塞锁（Blocking Lock）的权衡

1. **单处理器（Uniprocessor）**：
    
      
    - 自旋**完全没有意义**（单核上自旋会占满 CPU，导致持锁线程根本无法运行来释放锁），必须阻塞休眠并切换。
        
          
        
2. **多处理器（Multiprocessor）**：
    
      
    - **阻塞开销**：涉及 2 次完整的上下文切换（保存/恢复上下文、破坏 TLB 和 CPU 缓存工作集，约数千时钟周期）。
        
          
        
    - **决策准则**：
        
          
        - 若**临界区极短（预计等待时间 < 2 次上下文切换开销）**，采用自旋锁（Spinlock）更高效。
            
              
            
        - 若临界区耗时较长（涉及 I/O 或可能阻塞），必须使用阻塞锁（Blocking Lock）。
            
              
            
3. **自旋锁的使用禁忌**：
    
      
    - **绝对不能在持有自旋锁时进行 I/O**。
        
          
        
    - **不能嵌套可能阻塞的操作**。
        
          
        
    - **内核实现自旋锁时必须同时关闭本地中断**（防止持锁线程被时间片中断剥夺调度，导致其他 CPU 无限死等自旋）。
        
          
        
4. **混合锁（Hybrid Lock / 二阶段锁）**：
    
      
    - 先自旋一小段时间（如 ~1000 周期）；若仍未获取到锁，再调用系统调用陷入内核休眠阻塞，兼顾两者优势。
