**虚拟内存（Virtual Memory）**

  

  

**1. 增大页面大小（Page Size）会产生什么影响？**

  

  

- **解答** ：
    
      
    - **增加内部碎片（Internal Fragmentation）** ：内存分配的基本单位变大，当分配按页面大小向上对齐时，未使用的内存空间潜在增大。实际应用中这通常不是大问题，因为向上对齐到下一页边界所浪费的内存与程序本身的大小相比相对较小。
        
          
        
    - **减少页面数量** ：对于固定大小的物理内存，大页面意味着更少的页表项（PTE），从而使页表更小（查找速度也可能更快）。
        
          
        
    - **增加 TLB 覆盖范围（TLB Coverage）** ：TLB 的表项数量是固定的，每个表项覆盖更大的内存区域，从而降低 TLB 缺失率（Miss Rate）。
        
          
        
    - **增加缺页异常延迟（Page Fault Latency）** ：发生缺页时必须将整页数据加载进内存才能允许进程继续运行，大页面每次缺页需要等待更长的加载时间。
        
          
        
    - **提升交换 I/O 吞吐量（Swapping I/O Throughput）** ：对于固定容量的数据，大页面具有更高的 I/O 吞吐量，因为一页的内容在磁盘上连续存储，支持顺序访问。
        
          
        
    - **增加工作集大小（Working Set Size）** ：工作集定义为进程在某段时间窗口内访问的所有页面所关联的内存大小。页面越大，页面内包含大量未被使用数据的概率就越高，因此工作集大小通常随页面增大而增加。
        
          
        

**2. 为什么请求调页（Demand Paging）通常比预调页（Pre-paging）更普遍？**

  

  

- **解答** ：预调页需要预测未来（这很难做到），而且预测失误的惩罚可能很高（可能会将有用的页面换出以换入不需要的页面）。
    
      
    

**3. 描述四种页面置换策略并进行对比。**

  

  

- **解答** ：
    
      
    - **最佳置换算法（Optimal）**
        
          
        
          
        - 淘汰未来最长时间内不会被使用的页面。
            
              
            
        - 无法实现（需预知未来）。
            
              
            
        - 仅作为理论参考基准：实际算法越接近 Optimal 越好。
            
              
            
    - **先进先出（FIFO）**
        
          
        
          
        - 先进先出：淘汰最早调入的页面。
            
              
            
        - 易于实现。
            
              
            
        - 页面的驻留时长与使用频率并没有必然联系。
            
              
            
    - **最近最少使用（LRU）**
        
          
        
          
        - 淘汰最近最久未被访问的页面。
            
              
            
        - 假设长时间未被引用的页面在不久的将来也不太可能被引用。
            
              
            
        - 在满足局部性原理时表现良好。
            
              
            
        - 实现需要为每个页面记录时间戳，并在每次访存时更新。
            
              
            
        - 无法高效地纯硬件/软件实现。
            
              
            
    - **时钟置换算法（Clock）**
        
          
        
          
        - 在页框表中使用一个使用/引用位（Usage / Reference Bit）。
            
              
            
        - 页面被访问时置 1。
            
              
            
        - 扫描寻找牺牲页时，将经过的引用位置 0。
            
              
            
        - 淘汰遇到的第一个引用位为 0 的页面。
            
              
            

**4. 什么是系统抖动（Thrashing）？如何检测？如何解决？**

  

  

- **解答** ：
    
      
    - **定义** ：当所有进程的工作集大小之和超过了可用物理内存容量时，计算机花费越来越多的时间等待页面换入换出，即为系统抖动。
        
          
        
    - **检测方法** ：通过监控缺页异常发生频率（Page Fault Frequency）进行检测。
        
          
        
    - **解决措施** ：挂起并换出部分进程，以缓解物理内存压力。
        
          
        

**多处理器系统（Multi-processors）**

  

  

**5. 与每个 CPU 独立队列相比，使用全局调度队列有什么优缺点？在什么情况下使用哪种？系统的哪些特性会影响这一决策？**

  

  

- **解答** ：
    
      
    - **全局队列** 实现简单且能自动平衡负载，但在频繁发生调度事件或 CPU 数量较多（或两者兼有）时，全局调度队列会面临严重的锁竞争。另一个缺点是对待所有 CPU 均等，无法利用进程上次运行时在 CPU 本地残留的热缓存（Hot Caches）。
        
          
        
    - **每 CPU 独立队列** 提供 CPU 亲和性（Affinity），避免调度队列上的并发争用，但需要更复杂的机制来实现多核间的负载均衡。
        
          
        

**6. 在多处理器环境中，什么时候自旋锁（Spinlock / 忙等待，相对于阻塞休眠并在锁释放时被唤醒）是有意义的？**

  

  

- **解答** ：当平均自旋等待的时间小于“阻塞请求者、切换到另一进程、再切换回来并唤醒请求者”这一完整上下文切换流程的时间时，自旋是有意义的。
    
      
    

**7. 为什么抢占（Preemption）对自旋锁来说是一个问题？**

  

  

- **解答** ：自旋不仅浪费 CPU 时间，还会间接消耗总线带宽。在获取锁的设计中，系统应尽可能缩短自旋时间，这意味着应尽可能缩短持有者持锁的时间。如果持锁者被抢占挂起，持锁时间会被拉长跨越多个时间片，从而急剧增加其他等待者的自旋时间。
    
      
    

**8. 读前测试并设置锁（Read-before-test-and-set / Test-and-Test-and-Set）如何工作？为什么它能提高可扩展性？**

  

  

- **解答** ：代码实现可参考讲义。它能提高可扩展性，是因为自旋过程是在**普通的读指令**（而非原子 test-and-set 指令）上进行的，这使得自旋可以完全在 CPU 本地缓存的锁副本上发生。只有在锁状态发生改变时，才会因为使本地缓存行失效以及需要跨所有 CPU 独占内存访问的 test-and-set 指令而在总线上产生缓存一致性流量。

**9. 描述进程（或线程）时，*I/O 密集型（I/O bound）*和 *CPU 密集型（CPU bound）*分别是什么意思？**

  

  

- **解答** ：
    
      
    - **CPU 密集型** 进程的完成时间主要取决于它所获得的 CPU 执行时间。
        
          
        
    - **I/O 密集型** 进程的完成时间主要取决于处理其 I/O 请求所需的时间，CPU 时间对其完成时间的影响很小。
        
          
        

**10. 协作式多任务（Cooperative Multitasking）与抢占式多任务（Pre-emptive Multitasking）有什么区别？**

  

  

- **解答** ：协作式多任务中，线程必须明确主动释放 CPU；抢占式多任务中，线程没有选择，会被操作系统强制剥夺 CPU。
    
      
    

**11. 考虑传统 Unix 系统中使用的多级反馈队列（MLFQ）调度算法。它旨在偏向 I/O 密集型进程而非 CPU 密集型进程。这是如何实现的？它如何确保低优先级的 CPU 密集型后台作业不会发生饥饿？**

  

  

_(注：Unix 使用数值越小代表优先级越高，以下文本中的“高”和“低”均指优先级概念本身，而非 Unix 内部的数值。)_

  

  

- **解答** ：
    
      
    - I/O 密集型进程通常具有许多短暂的 CPU 突发（Burst）。当此类进程被调度时，通常不会用尽其分配的时间片。调度器会综合考虑消耗的 CPU 时间重新计算优先级，因此相比于从同一优先级开始但消耗更多 CPU 周期的进程，I/O 密集型进程最终会获得更高的优先级。
        
          
        
    - 低优先级进程最终仍会被调度，因为持续被调度的进程其优先级最终也会降低。
        
          
        
    - 同时，记录的 CPU 消耗量（用于计算优先级）会随时间发生**老化（衰减减少）**，因此未被调度的 CPU 密集型进程的优先级也会逐渐回升。
        
          
        

**12. 为什么一个假想的操作系统会倾向于总是调度同一地址空间内的线程，而不是切换到不同地址空间的线程？这样做是个好主意吗？**

  

  

- **解答** ：因为同地址空间内的线程上下文切换速度更快，且具备更好的缓存局部性。但如果过于频繁甚至总是这样做，会导致其他任务发生饥饿。
    
      
    

**13. 为什么时间片轮转（Round Robin）调度器不会使用极短的时间片来换取极高的应用响应速度？**

  

  

- **解答** ：从一个任务切换到另一个任务需要消耗 CPU 时间，而这种切换开销对应用程序的实际推进毫无贡献。如果切换非常频繁（时间片极短），可用 CPU 资源中相当大的一部分将被浪费在调度器的切换开销上。

**14. 请以接收输入（如来自串口）为例，描述_程序控制 I/O（Programmed I/O）_和_中断驱动 I/O（Interrupt-driven I/O）_。哪种技术通常能更高效地利用 CPU？请描述一种替代技术反而更高效的场景。**

  

  

- **解答** ：
    
      
    - **程序控制 I/O** ：CPU 通过持续读取状态寄存器来等待输入，直到寄存器指示输入数据已就绪；随后 CPU 读取传入数据，并返回继续读取状态寄存器等待后续输入。
        
          
        
    - **中断驱动 I/O** ：串口设备在数据准备就绪时向 CPU 发送中断。随后触发中断处理程序，确认接收中断、从设备读取数据并从中断返回。在不处理中断时，CPU 可以自由执行其他活动。
        
          
        
    - **效率对比** ：程序控制 I/O 通常效率较低，因为在没有输入时 CPU 处于忙等待（Busy waiting）状态。
        
          
        
    - **反例场景** ：当输入非常频繁，以至于中断处理的开销（进出中断处理程序的开销）超过了忙等待的平均时间时，程序控制 I/O 反而更高效。一个现实的例子是高速网络处理，此时几乎随时都有数据包到达。
        
          
        

**15. 文件系统代码调用了一个设备驱动例程（例如从磁盘执行 `read_block()`）。文件系统需要的数据已从磁盘发起请求，但尚未就绪。在此场景下，设备驱动程序通常会怎么做？**

  

  

- **解答** ：它们会阻塞在一个同步原语上，稍后当数据块就绪时由磁盘中断处理程序唤醒。
    
      
    

**16. 描述如何将 I/O 缓冲建模为_有界缓冲区生产者-消费者问题（Bounded-buffer producer-consumer problem）_。**

  

  

- **解答** ：
    
      
    - 以文件系统缓冲区缓存（Buffer Cache）为例：应用程序的写请求即为数据的**生产者**。操作系统必须在有界大小的缓冲区缓存中选择一个可用条目（或复用现有条目），如果缓冲区已满则阻塞等待，直到有空闲槽位。
        
          
        
    - 中断处理程序可以视为**消费者**：当向磁盘的写入完成后，中断处理程序将该缓冲区条目标记为**干净（Clean / 已消费）**，从而将其释放以供后续写入使用。
        
          
        

**17. 某个示例操作系统在当前运行应用程序的内核栈上执行其中断处理程序。这对中断处理程序代码施加了什么限制？为什么需要该限制？**

  

  

- **解答** ：
    
      
    - 中断处理程序**绝对不能阻塞等待资源**，因为阻塞中断处理程序会间接阻塞正在运行的应用程序。
        
          
        
    - 如果被中断的应用程序恰好持有中断处理程序所需的资源（例如内存缓冲区），系统将发生死锁。
