==**问题 1：以简单系统调用（如 getpid 或 uptime）为例，描述从在 C 库中调用该函数到该函数返回期间，通常涉及哪些处理过程。**==

  

==**概括流程：** 用户空间程序向 C 库发起函数调用（例如 `uptime`），该库函数会以适合硬件规范的方式设置系统调用。用户空间程序必须正确设置传参，然后触发陷入（Trap），从而使内核接管控制权并在内核空间处理该请求。在 MIPS 架构中，这是通过 `syscall` 指令实现的。==

  

==一旦内核获得控制权，便会保存用户态上下文（User State）。内核执行必要的安全与合理性检查，随后尝试完成该请求。以 `uptime` 为例，它会复制一个计数器的值（该计数器通常从系统开机起按秒计数）。接着恢复用户态上下文，将计数器的值放入栈或寄存器中，并跳转返回到用户空间。C 库例程读取内核刚写入的栈/寄存器中的数据，并将其返回给用户空间程序。==

  

参考材料详见：`[http://cgi.cse.unsw.edu.au/~cs3231/07s1/lectures/lect03.pdf](http://cgi.cse.unsw.edu.au/~cs3231/07s1/lectures/lect03.pdf)`（包含系统调用的全部相关内容，第 64 页给出了该过程的详细示意图）。

  

**具体底层执行步骤：**

  

- **设置所需的系统调用参数**：与普通非系统调用函数相同，但还需要将**系统调用号**存入 `$v0` 寄存器。
    
      
    
- **执行 syscall 指令**：替代原本的 `jal $function_label_here`，此时执行的汇编指令为 `syscall`。
    
      
    
- **这将在 CPU 中触发一个异常（Exception），产生以下效果**：
    
      
    - **程序计数器（PC）跳转至 `0x8000_0080`**（假设系统已完成初始化；该值根据状态寄存器的设定可能有所不同）。
        
          
        - 注意：这正是 `kseg0` 的起始地址，其最高字节的首位被翻转了。
            
              
            
    - **协处理器寄存器 `c0_epc` 保存被异常覆盖前的 PC 值**：
        
          
        - 这正是系统知道稍后该返回到何处执行的依据。
            
              
            
    - **设置 `c0_cause` 寄存器**：
        
          
        - 在本例中，它提供必要的信息使我们得知当前需要处理的是一个系统调用（Syscall）。
            
              
            
    - **修改 `c0_status` 寄存器**（对其执行左移 2 位 `<< 2` 操作，并将 8 到 15 位置位）：
        
          
        - 将原本表示“当前处于用户模式”和“当前允许中断”的位值推入该寄存器的“先前（previous）”部分，进而将先前的位值推入“历史（old）”部分。
            
              
            
        - “当前处于用户模式”与“当前允许中断”位于最右侧的位，因此 `<< 2` 使得它们被置 0。
            
              
            
        - 此时中断被关闭，CPU 运行在特权模式下，这意味着我们可以执行类似 `mfc0` 的特权指令。
            
              
            
        - 注：对于非系统调用的内核入口，可能还会设置其他协处理器寄存器。
            
              
            
- **设置内核栈指针**：此时 `$sp` 仍保存着用户级栈指针的值。因此我们先将其暂存到 `$k1` 寄存器（或其它暂存位置）。
    
      
    
- **检查来源的状态上下文**：通过 `c0_status` 的第 8 到 15 位配合位掩码（Bitmask）来实现。
    
      
    - 将 `c0_status` 保存到另一个内核寄存器并与位掩码进行按位与操作。
        
          
        
    - 这将判断当前是否需要获取内核栈：如果刚才是在内核栈上被中断的，则跳过后续这段栈获取逻辑。
        
          
        
- **加载内核栈**：我们不再需要 `$k0`（此前仅用于分支判断），使用如下指令将其加载为目标内核栈：
    
      
    - `lw $k0 curkstack`：获取内核栈起始地址。
        
          
        
    - `sw $sp 0($k0)`：解引用存放到内核栈起始处。
        
          
        
- **保存异常原因**：执行 `mfc0 $k0, c0_cause`。
    
      
    
- **仅通过修改以下三个寄存器，即可开始切换上下文**：
    
      
    - `$k1`：保存前一个栈指针（用户栈指针）。
        
          
        
    - `$sp`：持有当前栈指针，允许我们将其切换为正确的内核栈。
        
          
        
    - `$k0`：保存状态（根据讲义；OS/161 源码中为 `curcpu`）。
        
          
        
- **切换至内核栈**（见上文）。
    
      
    
- **将寄存器保存至内存（栈）中以保护现场**：
    
      
    - 手动使用 `sw`（注：原英文笔误写为 lw）汇编指令将每个寄存器的值存入内存特定位置，从而让 `$a0` 指向一个内存地址——这实际上指向了一个 `trapframe` 结构体，用于后续执行 `jal`。
        
          
        
    - 我们不仅保存通用寄存器，还会保存协处理器寄存器以及先前的栈指针。
        
          
        
- **此时，系统已建立内核上下文，并完整保存了用户上下文**。
    
      
    
- **执行 `jal mips_trap`**（进入 C 语言代码）：
    
      
    - 此时可以利用用户栈中的信息以及陷入路径进入具体内核处理逻辑：例如是否分派给 `read()`？可通过读取 `$v0` 保存的值来判断。
        
          
        
- **执行具体的内核操作（如 `read()`）**。
    
      
    
- **恢复通用寄存器与现场**。
    
      
    
- **切换回用户栈**：
    
      
    - 将保存自 `c0_epc` 的返回 PC 地址加载到 `$k1` 或 `$k0` 寄存器中。
        
          
        
    - 执行 `jr $k0/1`，并在分支延迟槽中执行 `rfe` 指令。
        
          
        
    - `jr` 指令使 CPU 跳回原本发起调用的指令位置。
        
          
        
    - `rfe` 指令将 CPU 恢复到发生陷入前的特权模式（大致如此）。
        
          
        
- **返回到应用程序继续执行**。
    
      
    

==**问题 2：为什么当数据位于内存而非寄存器中时，操作系统在访问系统调用的输入参数（或生成输出结果）时必须格外谨慎？**==

  

==操作系统必须验证所读写的内存地址是否有效，且必须属于发起请求的进程。操作系统必须防止进程破坏其他进程的数据，或非法读取属于其他进程的内存。==

  

==当输入来自内存时，操作系统必须谨慎处理，原因在于：==

  

- ==应用程序提供的输入或输出地址可能是**非法/越界的内存区域**；==
    
      
    
- ==该地址可能是**合法但已被置换（Page out）到磁盘上的虚拟内存页**；==
    
      
    
- ==若应用程序是多线程的，该内存地址对应的内容**在内核访问期间可能会被其他线程动态篡改**。==
    
      
    

==本质上，操作系统必须确保自身不会因为按应用程序的指示访问内存而遭到破坏、崩溃或安全机制被绕过。==

  

**问题 3：将安全检查放在 C 库中是个好主意还是坏主意？为什么？**

  

将安全检查放在 C 库中**完全无法提供安全保障（是个坏主意）**。因为使用 C 库仅仅是用户空间程序的一种自选便利方式，没有任何机制能阻止恶意用户程序绕过 C 库，直接构造任意参数（包含恶意数据）发起底层 `syscall` 指令。所有的安全与权限检查必须在**内核空间**中执行，因为用户空间程序无法对内核施加非法影响，也无法绕过内核的安全检查。
