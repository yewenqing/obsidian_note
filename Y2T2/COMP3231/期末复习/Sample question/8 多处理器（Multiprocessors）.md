==**与单处理器相比，描述为什么在多处理器系统上使用自旋锁可能比阻塞锁更合适。在多处理器系统上，自旋与阻塞之间是否存在权衡？请进行讨论。**==

  

  

==在单处理器上，自旋锁通常是不适用的。单处理器上的进程要么能立即获取自旋锁，要么就会无限自旋，等待另一个进程释放锁。然而，由于第一个进程正占用处理器进行自旋，另一个进程根本无法运行来释放锁。因此，在单处理器上阻塞休眠是更好的选择。==

  

==在多处理器上，持有锁的线程当前可能正在另一个处理器上活跃运行，并且随时可能释放该锁。如果在多处理器上平均自旋等待的时间小于“从锁请求者发生上下文切换移出、再切换回来”的平均开销，那么使用自旋锁就是值得的。==

  

==**在多处理器系统上使用单个就绪队列是一个好主意吗？为什么？**==

  

  

==使用单个共享就绪队列并不是一个好主意，原因有两点：==

  

- ==就绪队列是一个共享资源，当大量处理器都想调度其下一个任务时，它会成为性能瓶颈。例如，如果队列受单把锁保护，当多个处理器试图调度工作时，单一共享就绪队列会引入锁竞争。==
    
      
    
- ==它无法保证进程尽可能在同一个 CPU 上运行，从而会导致更多的缓存未命中（Cache Misses）。==
    
      
    

==然而，如果多处理器系统中的 CPU 数量足够少，使得上述瓶颈不构成问题，那么单个共享队列也是一个好主意。这是因为其实现简单，并且能够提供自动的负载均衡。==

  

**什么是线程亲和性？为什么它能够提升性能？**

  

  

线程亲和性是指在多处理器机器中，调度器会尝试将线程调度到某一个或某些特定的处理器上运行。这增加了线程被调度到其之前运行过的处理器上的概率。这通常能提升性能，因为该处理器上已经积累了与该线程相关的缓存条目（Cache Entries），因此线程在后续运行时可能无需再次重新加载这些缓存条目。

  

**比较测试并设置（Test-and-Set）与读前测试并设置（Test-and-Test-and-Set）。**

  

  

- **测试并设置（Test-and-Set, TSL）** 是一种忙等待原语，在对锁进行自旋时通常会导致严重的锁竞争。这会导致频繁的总线锁定，引起严重的总线争用，并拖慢其他 CPU 的通信速度（无论它们是否需要该锁）。缓存机制无法减少这种总线争用——要么 TSL 锁定了整条总线，要么总线被用于同步与锁相关的缓存条目。因此，TSL **无法** 随着处理器数量的增加而良好扩展。
    
      
    
- **读前测试并设置（Test-and-Test-and-Set, TTSL）** 则是先在本地缓存中的锁值上自旋读取，当检测到锁被释放时，才使用 TSL 尝试去获取它。由于该方法是在本地缓存内容上自旋，所以在锁被实际释放、缓存条目需要更新/锁需要被获取（Set）之前，完全不会产生总线争用。与 TSL 相比，TTSL 更有效地利用了缓存，并显著减少了总线争用。但是，它无法保证各 CPU 获取锁的先后顺序，可能会导致饥饿——哪个 CPU 能够最先设置锁，哪个 CPU 就能获取该锁（这也是 TSL 的问题）。尽管 TTSL 的性能优于 TSL，但它同样 **无法** 随处理器数量无限制扩展，因为当处理器数量足够多时，在抢锁瞬间依然会引起严重的总线争用。
