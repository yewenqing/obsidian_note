## 1. MIPS R3000 架构与汇编基础

### 1.1 架构概述

- **历史背景**：由 MIPS Computer Systems 于 1988 年开发，作为 R2000 的后续版本，在 90 年代广泛用于 Silicon Graphics IRIS、DEC workstation 以及索尼 PlayStation 等设备。
    
- **精简指令集（RISC）**：所有指令均为固定长度的 **32 位（4 字节）**。
    
- **加载/存储架构（Load/Store Architecture）**：不能在一条指令内同时进行复杂的算术运算并读写内存。除了特定的加载（Load）和存储（Store）指令外，没有任何指令可以直接操作内存。指令要么处理算术/逻辑，要么进行数据加载/存储，要么进行分支跳转。
    

### 1.2 核心指令集与延迟效应（Delay Effects）

MIPS R3000 在硬件设计上暴露出了一些时序上的“奇特设计”（Quirks），需要软件或编译器来进行配合：

- **内存操作指令**：
    
    - 使用 `L` 代表加载，`S` 代表存储；以 `W`（字长，32位）、`B`（字节，8位）、`H`（半字，16位）等区分数据长度。
        
    - 示例：`sw r4, (r5)` 将 `r4` 的内容存入 `r5` 指向的内存；`lw r3, (r7)` 将 `r7` 指向的内存内容加载到 `r3`。
        
- **加载延迟（Load Delay）**：
    
    - **机制**：从内存加载数据需要经过数据缓存（D-cache）或实际内存，耗时较长。硬件限制导致数据在加载指令后的**紧接着下一条指令中不可用**，即加载指令实际上需要 2 个周期才能完成。
        
    - **软件应对**：在使用该目标寄存器前，必须插入其他无关指令或空操作 `nop` 垫平延迟。
        
- **算术与逻辑指令**：
    
    - 完全基于寄存器到寄存器操作。例如 `add r3, r2, r1` 实现 $r3 = r2 + r1$，左侧寄存器为输出目标。
        
    - 常用指令包括：`add`, `sub`, `and`, `or`, `xor`, `sll`（逻辑左移）, `srl`（逻辑右移），以及通用移动 `move r2, r1`。
        
- **立即数操作数（Immediate Operands）**：
    
    - 常量直接编码在指令内部，在 32 位指令空间中**仅占用 16 位**。
        
    - 示例：`addi r2, r1, 2048`（$r2 = r1 + 2048$），`li r2, 1234`（加载立即数 1234 到 `r2`）。
        

```
立即数指令编码示意图 (32-bit):
+---------+---------+---------+-------------------------+
|  Opcode |   RS    |   RT    |    Immediate Value      |
|  (6-bit)| (5-bit) | (5-bit) |       (16-bit)          |
+---------+---------+---------+-------------------------+
```

### 1.3 分支延迟槽（Branch Delay Slot）

- **现象**：由于处理器采用五级流水线（5-Stage Pipeline）设计：**IF**（指令获取） $\rightarrow$ **RD**（读寄存器/ALU计算） $\rightarrow$ **ALU**（算术逻辑单元） $\rightarrow$ **MEM**（内存访问） $\rightarrow$ **WB**（寄存器写回）。
    
- **延迟机制**：在执行分支（Branch）或跳转（Jump）指令时，下一条指令在跳转生效前就已经进入了流水线（已经执行了指令获取）。因此，**紧跟在分支/跳转指令后面的那条指令（即处于延迟槽内的指令）总是会被执行**，无论跳转条件是否达成。
    
- **软件处理**：编译器通常会重排程序流，将跳转前最后一步要做的无关指令放入延迟槽中；若无法优化，则必须放置一条空操作 `nop` 指令以防引起不可预测的逻辑错误。
    

### 1.4 函数调用：跳转并链接指令（JAL）

- `jal 1f` 指令用于实现函数调用。它会跳转到指定标签，并自动将当前程序计数器值加上 8（即 `PC + 8`）保存到返回地址寄存器 **`r31`（ra）** 中。
    
- **为什么是 PC + 8**：因为跳转指令后紧跟一个 4 字节的延迟槽指令（`PC + 4`），同样会被执行。为了在函数返回时跳过该延迟槽，逻辑上必须返回到 `PC + 8` 的下一条指令。
    
- 函数结束时，使用寄存器跳转指令 `jr r31` 实现返回。
    

### 1.5 编译器寄存器约定 (Gcc Register Conventions)

MIPS R3000 共有 32 个通用寄存器，编译器通过以下标准约定来共享和保护它们：

|**寄存器编号**|**常用名称**|**核心用途 PDF**|**维护者责任 TXT**|
|---|---|---|---|
|**`r0`**|`zero`|硬编码为 0，只读|-|
|**`r1`**|`at`|汇编器临时寄存器（Reserved for Assembler）|-|
|**`r2 - r3`**|`v0 - v1`|子程序返回值（非浮点型）|-|
|**`r4 - r7`**|`a0 - a3`|函数调用的前四个参数|-|
|**`r8 - r15, r24 - r25`**|`t0 - t9`|临时寄存器，子程序可自由覆盖而无需保存|**调用者保护 (Caller-saved)**|
|**`r16 - r23`**|`s0 - s7`|静态/保存寄存器，子程序若要使用必须先保存并在退出前恢复|**被调用者保护 (Callee-saved)**|
|**`r26 - r27`**|`k0 - k1`|专供中断/陷阱内核处理程序使用，用户态不可触碰|-|
|**`r28`**|`gp`|全局指针，用于方便访问静态/外部变量|-|
|**`r29`**|`sp`|**栈指针（Stack Pointer）**，指向当前栈帧底部|-|
|**`r30`**|`s8 / fp`|**帧指针（Frame Pointer）**，指向栈帧起始处，方便调试器在栈大小动态变动时精确定位局部变量|-|
|**`r31`**|`ra`|子程序的返回地址（由 `JAL` 隐式修改）|-|

> **补充思考：为什么现代通用 CPU 选择乱序执行（Out-of-Order, OOO）？**
> 
> 软件语言通常是顺序（In-order）的，但硅片电路更适合多计算单元并行（Out-of-order）。由于总线和硬件资源限制，数据从芯片一侧传到另一侧需要多个周期，为了不让高速计算单元一直卡死等待缓慢的内存，现代 CPU 内部实现了复杂的硬件乱序重排和投机猜测（这也是 Spectre/Meltdown 漏洞的基础）。而 MIPS 和安腾（Itanium）则是少数把这种时序约束直接作为“软件问题”丢给编译器的经典例外。

## 2. 进程与多线程模型

### 2.1 传统进程模型 (The Process Model)

- **单线程进程**：在一个传统进程中，任意时刻只能有一个程序处于活跃状态，整个进程公用**一个程序计数器（PC）**。
    
- **基本内存布局**：单线程进程的地址空间至少包含三个核心段：
    
    - **Text 段**：包含只读的代码指令。
        
    - **Data 段/堆（Heap）**：存放全局变量和动态分配的内存空间（通过 `malloc()`），其边界通常**动态向上增长**。
        
    - **Stack 段**：存储函数调用激活记录（栈帧）和局部变量，其边界**动态向下增长**（向 0 地址方向）。
        

### 2.2 多线程进程模型 (Multi-Threaded Process)

- 进程是**资源分配**的边界，而线程是独立执行（调度）的单元。
    
- **共享的资源（进程级项目）**：地址空间、全局变量、打开的文件描述符、子进程信息、待处理报警、信号处理程序及统计信息。
    
- **独享的资源（线程级项目）**：**程序计数器（PC）**、独立的一套**寄存器状态**、独立的栈（Stack）以及线程状态。
    

```
多线程进程内存布局 (Regions of Address Space):
+------------------------------+  高地址
|       Thread 1 Stack          |   (向下增长)
+------------------------------+
|       Thread 2 Stack          |   (各个线程独立的栈可能交错分布)
+------------------------------+
|     Sparse Gap / Memory Map  |   (地址空间大, 2^32 字节或更多, 许多区域处于稀疏预留状态)
+------------------------------+
|          Heap                |   (动态向上增长)
+------------------------------+
|          Data                |   (初始全局变量)
+------------------------------+
|          Text                |   (初始代码指令)
+------------------------------+  低地址
```

## 3. 线程的两种实现策略及权衡

应用程序在实现 POSIX 线程标准接口（如 `pthread_create`, `pthread_mutex_lock`）时，有两种根本截然不同的底层支持方式：

### 3.1 用户级线程 (User-Space Threads / Many-to-One)

所有线程管理逻辑完全在一套用户态的运行时支持库（Run-time system）中实现，内核完全不知道线程的存在，只视其为一个普通的单线程进程。

- **数据结构**：线程控制块（TCB）、就绪/阻塞队列以及分发器（Dispatcher）全部维护在用户空间；内核只维护进程表（Process Table）。
    
- **协作式多线程（Co-operative Multithreading）**：线程没有定时器中断可以直接递送，必须通过显式调用 `yield()` 主动让出 CPU。
    
- **优缺点分析**：
    
    - **优点 (Pros)**：
        
        1. **极高的性能**：线程创建、销毁和切换速度极快，不需要陷入内核（无 Traps/Syscall 异常代价）。
            
        2. **高度可定制**：调度算法（如优先级）可以完美适配特定应用程序的需求。
            
        3. **可扩展性强**：能够支持应用级别的海量大并发线程，只受普通虚拟内存限制（而内核内存非常受限）。
            
        4. 可以在任何不支持线程的 Legacy 操作系统上轻松实现。
            
    - **缺点 (Cons)**：
        
        1. **单点阻塞导致全盘卡死**：如果进程中的任何一个线程发起了阻塞系统调用（如等待磁盘 I/O）或发生缺页中断（Page Fault），**整个进程和内部所有其他线程都会被一起阻塞**。
            
        2. **无法真正并行**：由于内核只分发一个内核态调度名额，该应用**无法利用多核/多 CPU 硬件优势**。
            
        3. 协同式设计极易因为某个设计不良的死循环线程而垄断整个进程的 CPU 时间。
            

### 3.2 内核级线程 (Kernel-provided Threads / One-to-One)

线程直接由操作系统内核来实现和管理，TCB 存储在内核空间中，是传统 PCB 的执行上下文子集。

- **线程关系**：每一个用户线程直接映射到一个独立的内核级线程，由统一的内核调度器管理所有线程。所有线程操作接口（`create`, `exit`, `wait`）均通过**系统调用**陷入内核完成。
    
- **优缺点分析**：
    
    - **优点 (Pros)**：
        
        1. **真正的抢占式多线程（Preemptive）**：内核能通过时钟中断强制剥夺耗时线程的 CPU。
            
        2. **完美的硬件并行**：内核可以直接将属于同一个进程的不同线程分发到不同的 CPU 核心上执行。
            
        3. **克服阻塞限制**：一个线程因阻塞系统调用（I/O）而挂起时，内核可以平滑地调度同进程内的其他线程继续工作，实现 **I/O 延迟与计算的重叠**。
            
    - **缺点 (Cons)**：
        
        1. **高昂的开销**：线程的创建、销毁、阻塞或唤醒全部依赖内核切入和切出，性能代价显著高于用户级等价操作。
            

> **OS/161 内核栈设计决策**： OS/161 采用的是“**每个用户线程拥有一个内核栈**”的经典结构。当用户线程陷入内核时，它有自己专属的、小巧的内核栈来进行内核代码调用和阻塞操作。另一种替代设计是“每个 CPU 核心一个内核栈”，这能有效缓解内核栈堆叠带来的大范围物理内存开销压力。

## 4. 上下文切换机制 (Context Switch)

### 4.1 核心术语与触发时机

- **概念定义**：
    
    - **线程上下文切换**：涉及保存和恢复与某线程紧密关联的硬件状态（寄存器、PC、SP等）。
        
    - **进程上下文切换**：除了上述内容，还必须切换与进程高度相关的外部环境状态，如虚拟内存映射（Memory Maps / 页表等）。
        
- **切换触发的前提**：必须是在控制流已经进入操作系统内核的节点：
    
    1. **系统调用（System Call）**：当系统调用面临阻塞或进程主动调用 `exit()` 时触发。
        
    2. **硬件异常（Exception）**：例如分段错误（Segfault）导致进程无法继续运行时发生。
        
    3. **外设中断（Interrupt）**：主要是定时器中断（Timer Interrupt）触发，这是实现进程公平抢占式分发的基础。
        

### 4.2 典型硬件中断/上下文切换全流程

当最底层的硬件中断产生时，系统透明地保存和恢复上下文需要经历以下标志性步骤：

```
+-------------------------------------------------------------+
| 1. 硬件自动压栈保存程序计数器 (PC) 等基本信息                      |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 2. 硬件从中断向量表 (Interrupt Vector) 处自动加载新内核 PC      |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 3. 汇编语言预处理过程：在内核栈上开辟空间, 保存全部通用寄存器          |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 4. 汇编代码设置好全新的内核环境栈 (Kernel Stack)                  |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 5. 调用 C 语言中断服务例程 (ISR) 运行，读取并缓冲物理输入           |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 6. 核心调度器 (Scheduler) 介入，决策出接下来该去运行哪个新进程      |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 7. C 语言处理函数执行完毕，返回至底层的汇编还原代码空间             |[cite: 2]
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 8. 汇编过程恢复寄存器，退出内核，启动运行全新的“当前进程”             |[cite: 2]
+-------------------------------------------------------------+
```

### 4.3 具体的内存栈帧变化轨迹 (以内核级线程切换为例)

在单核处理器上，线程切换时其专属内核栈呈现出精细的递进布局：

1. **用户态正常运行**：处理器寄存器 SP 指向用户空间栈[cite: 2]。
    
2. **陷入内核界限**：由于 syscall 或中断发生，硬件和底层汇编首先在内核栈底部强制推入一个**陷阱帧（Trapframe，也叫异常帧）**，记录了用户被阻断处的 `PC`、`SP` 和通用寄存器内容。
    
3. **C 调用链累积**：内核处理逻辑调用了多层 C 函数，内核栈上向上构建起了一系列 **C 语言激活栈帧（C Activation Stack）**。
    
4. **触发线程让出**：C 代码最终决定要执行线程切换，在进行任何实质动作前，它会再次向栈中推入一部分**内核上下文状态（Kernel State）**。
    
5. **切换核心**：由于是在单核环境下，所有当前未处于运行状态的线程必然都停留在同一个切出函数内部。此时只需要将当前的 `SP` 寄存器值写入旧 TCB，并从新 TCB 的特定字段中读取出其先前保存的 `SP` 值，内存栈便彻底完成了乾坤大挪移。
    
6. **逆向还原弹栈**：处理器在新线程的内核栈上层层剥离 C 激活帧，利用底部的陷阱帧将保存的用户态寄存器和 `PC`/`SP` 重新灌入 CPU 硬件，控制流平滑返回至新进程的用户态空间继续前行。
    

## 5. 源码剖析：OS/161 核心切换实现

### 5.1 调度层：`thread_switch`

OS/161 调度器在挑出目标线程后，本质上是调用了特定于架构的汇编过程 `switchframe_switch` 来实施栈转换：

C

```
// 简化后的 OS/161 线程切换骨架[cite: 2]
static void thread_switch(threadstate_t newstate, struct wchan *wc) {
    struct thread *cur, *next;
    cur = curthread;
    
    do {
        // 从当前 CPU 的就绪队列头部摘取下一个就绪线程[cite: 2]
        next = threadlist_remhead(&curcpu->c_runqueue);
        if (next == NULL) {
            cpu_idle(); // 队列为空则让 CPU 闲置等待[cite: 2]
        }
    } while (next == NULL);

    /* 实施核心的底层汇编栈切换 */
    switchframe_switch(&cur->t_context, &next->t_context);[cite: 2]
}
```

### 5.2 核心底层汇编：`switchframe_switch` (位于 switch.S)

`switchframe_switch` 是一个极具欺骗性的特殊汇编例程，它满足 C 语言调用约定，但其真正的魔幻在于：**由 A 线程调用进去，却从 B 线程的返回路径里退出来**[cite: 1, 2]。

- **输入参数**：
    
    - `a0`：包含旧线程 TCB 中存放 `switchframe` 指针的地址[cite: 2]。
        
    - `a1`：包含新线程 TCB 中存放 `switchframe` 指针的地址[cite: 2]。
        
- **寄存器保护细节**：由于它是以普通 C 函数调用的形式进入的，编译器已经自动在之前保存了 Caller-saved 寄存器。此汇编过程**只需负责保存 10 个 Callee-saved 寄存器**即可（包括 `s0-s6`, `s8`, `gp`, `ra`），其中 `s7` 被内核锁定用来持有当前的 `curthread` 变量，无需此处手工处理[cite: 2]。
    

#### 汇编实现代码

[cite: 2]：

代码段

```
.text
.globl switchframe_switch
.type switchframe_switch,@function

switchframe_switch:
    /* 1. 在当前内核栈上开辟空间用于容纳 10 个寄存器 (10 * 4 = 40 字节) */
    addi $sp, $sp, -40[cite: 2]

    /* 2. 依次将必备的 Callee-saved 寄存器压入栈中 */
    sw $ra, 36($sp)    # 保存返回地址[cite: 2]
    sw $gp, 32($sp)    # 保存全局指针[cite: 2]
    sw $s8, 28($sp)    # 保存帧指针[cite: 2]
    sw $s6, 24($sp)[cite: 2]
    sw $s5, 20($sp)[cite: 2]
    sw $s4, 16($sp)[cite: 2]
    sw $s3, 12($sp)[cite: 2]
    sw $s2,  8($sp)[cite: 2]
    sw $s1,  4($sp)[cite: 2]
    sw $s0,  0($sp)[cite: 2]

    /* 3. 核心节点：把当前已经全密封的物理栈指针 SP 存入旧线程的 TCB 空间 (a0) */
    sw $sp, 0($a0)[cite: 2]

    /* =====================================================================
     *  此时，旧线程 A 彻底冻结。下面开始移花接木，换成新线程 B 的世界线。
     * ===================================================================== */
```
