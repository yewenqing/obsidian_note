

# 操作系统笔记：并发与同步（Part II）

## 一、 并发核心概念与复习

### 1. 临界区（Critical Regions）

- **定义**：临界区是指访问**共享资源**的一段代码区域 。
    
- **核心需求**：必须确保**互斥（Mutual Exclusion）**，即同一时间绝不允许两个线程/进程同时处于临界区内，否则会引发竞态条件（Race Condition） 。
    

### 2. 硬件支持：测试并设置（Test-and-Set）

许多硬件提供了一条原子性的汇编指令（如 Test-and-Set），允许在硬件层面上**原子性地**检查并转变状态，以确保多核/多CPU竞争时只有一个获胜并持有锁 。

- **优点**：简单（易于证明其正确性）、可在用户态使用、支持任意数量的处理器和锁变量 。
    
- **缺点（自旋锁/忙等待锁的代价）** ：
    
    - **消耗 CPU**：未获取锁的线程会陷入死循环（Spinning），白白浪费 CPU 周期 。
        
    - **线程被挂起时的灾难**：如果持有锁的线程被操作系统放入睡眠状态，等待它的线程仍会不停自旋，极大地浪费时间 。
        
    - **可能导致饥饿（Starvation）**：当一个进程离开临界区而有多个进程在等待时，硬件无法保证公平分配 。
        

### 3. 解决忙等待：阻塞机制（Sleep / Wakeup）

为了消除自旋锁的弊端，操作系统引入了阻塞机制，让线程状态从运行/就绪转变为等待 ：

- **Sleep**：当进程等待某个事件时，调用 Sleep 将自己**阻塞（Block）**，挂起到事件队列，出让 CPU 。
    
- **Wakeup**：当事件发生时，由事件触发者（另一个进程）调用 Wakeup 来解冻/唤醒（Unblock）处于睡眠中的进程 。
    
- **注意**：唤醒一个本身就处于就绪或运行状态的进程是没有任何效果的 。
    

## 二、 经典并发难题一：生产者-消费者问题（Bounded Buffer Problem）

### 1. 问题模型

- **有界缓冲区**：缓冲区大小固定为 $N$ 槽 。
    
- **生产者（Producer）**：生产数据项并将其存入缓冲区 。当缓冲区**满**时，生产者必须睡眠；当有空位时被唤醒 。
    
- **消费者（Consumer）**：从缓冲区取出数据项并消费 。当缓冲区**空**时，消费者必须睡眠；当有数据时被唤醒 。
    

### 2. 简单 Sleep/Wakeup 方案的缺陷（为何不可行？）

早期的伪代码试图在发现 `count == N` 或 `count == 0` 时直接调用 `sleep()` 。这会引入两大致命问题：

1. **对缓冲区和计数器（count）的无控制并发访问**：多个线程同时对 `count++` 或 `count--` 进行非原子性操作会导致数据混乱 。
    
2. **锁与睡眠冲突导致的永久死锁**：
    
    - 如果不加锁保护条件测试，可能在消费者“注意到空”到“执行睡眠”的间隙被生产者打断，生产者发出 `wakeup` 信号时消费者尚未睡着（信号丢失），随后消费者永久睡死 。
        
    - 如果在持有锁的情况下调用 `sleep()`，由于该结构被死死锁住，其他线程永远无法进入临界区改变 `count`，从而导致整个系统彻底瘫痪（死锁） 。
        

> **核心症结**：**检查条件**与**进入睡眠**这两个动作必须是**原子性的（Atomic）** 。

## 三、 标准同步原语及其在 OS/161 中的实现

针对上述难题，计算机科学引入了三种标准的同步原语，也是 OS/161 核心提供的基础库 ：

### 1. 锁（Locks / Mutexes）

锁主要用于保障细粒度的互斥访问，在临界区两端使用 。

- **OS/161 接口** ：
    
    C
    
    ```
    struct lock *lock_create(const char *name); // 创建锁
    void lock_destroy(struct lock *);           // 销毁锁
    void lock_acquire(struct lock *);           // 获取锁（若被占用则阻塞）
    void lock_release(struct lock *);           // 释放锁
    ```
    
- **不变量约束**：获取与释放必须严格遵循一比一的匹配路径 。
    

### 2. 信号量（Semaphores）

由 Dijkstra 于 1965 年提出，内部维护一个计数器和一个阻塞进程队列 。

- **操作定义** ：
    
    - **P() / wait() / down()**：探测/测试 。若 `count > 0` 则递减并继续；若 `count <= 0` 则将当前线程投入等待队列并阻塞 。
        
    - **V() / signal() / up()**：递增/发信号 。`count++`，若有阻塞线程则唤醒其中一个，否则保留该信号令牌 。
        
- **原子性保障**：P 和 V 操作属于底层原语，内部通过禁用中断或极短暂的底层自旋锁来实现原子化 。
    
- **锁的泛化**：当信号量的初始计数 `initial_count = 1` 时，它等价于一个互斥锁（Mutex） 。
    
- **OS/161 接口** ：
    
    C
    
    ```
    struct semaphore *sem_create(const char *name, int initial_count);
    void sem_destroy(struct semaphore *);
    void P(struct semaphore *);
    void V(struct semaphore *);
    ```
    

#### 💡 信号量解决生产者-消费者问题

使用 3 个信号量：一个互斥锁 `mutex`，一个统计空位的 `empty`，一个统计满位的 `full` 。

C

```
// 共享变量
Semaphore mutex = 1;  // 控制互斥访问缓冲区
Semaphore empty = N;  // 空闲缓冲区单元数量
Semaphore full = 0;   // 充满数据的缓冲区单元数量

// 生产者进程
void producer() {
    while(true) {
        // 1. 生产一个产品 item
        item = produce_item(); 
        
        // 2. 检查是否有空位（empty - 1），如果没有空位则在此阻塞
        P(empty); 
        
        // 3. 锁定缓冲区，准备放入
        P(mutex); 
        
        // 4. 将产品放入缓冲区
        put_item_into_buffer(item); 
        
        // 5. 解锁缓冲区
        V(mutex); 
        
        // 6. 告诉消费者：产品多了一个（full + 1），并唤醒可能在等待的消费者
        V(full); 
    }
}

// 消费者进程
void consumer() {
    while(true) {
        // 1. 检查是否有产品（full - 1），如果没有产品则在此阻塞
        P(full); 
        
        // 2. 锁定缓冲区，准备取出
        P(mutex); 
        
        // 3. 从缓冲区中取出一个产品
        item = remove_item_from_buffer(); 
        
        // 4. 解锁缓冲区
        V(mutex); 
        
        // 5. 告诉生产者：空位多了一个（empty + 1），并唤醒可能在等待空间的生产者
        V(empty); 
        
        // 6. 消费掉这个产品
        consume_item(item); 
    }
}```

### 3. 管程（Monitors）与条件变量（Condition Variables）

为了避免程序员手动编写 P/V 操作带来的错写、漏写或语序颠倒等灾难性Bug，Hoare（1974）提出了管程（高级语言构造） 。

- **管程（Monitor）**：
    
    - 将共享数据、局部变量和一组操作方法封装在一个特殊的模块内 。
        
    - **编译器机制**：管程的互斥访问由编译器自动生成代码控制，**在任何时刻，只能有一个线程在管程内部活跃** 。若已有线程在内部，其他调用者会自动进入入口队列（Entry Queue）阻塞挂起 。
        
    - 注：OS/161 作为 C 语言内核并不直接具备面向对象管程的原语，但其思想通过“显式锁 + 条件变量”组合来落地 。
        
- **条件变量（Condition Variables）**：
    
    - 用于在持有管程互斥权的前提下，因某些逻辑条件不满足而让线程让出互斥权并睡眠 。
        
    - **OS/161 接口与规范** ：
        
        C
        
        ```
        struct cv *cv_create(const char *name);
        void cv_destroy(struct cv *);
        void cv_wait(struct cv *cv, struct lock *lock);     // 释放锁并阻塞
        void cv_signal(struct cv *cv, struct lock *lock);   // 唤醒一个等待者
        void cv_broadcast(struct cv *cv, struct lock *lock);// 唤醒所有等待者
        ```
        
    - **极其重要的行为规范**：
        
        1. **必须持有锁**：调用 `cv_wait`、`cv_signal`、`cv_broadcast` 时，当前线程**必须已经持有**传入的该互斥锁 。
            
        2. **Wait 的原子手放**：`cv_wait` 会在内部**原子性地释放锁并使线程进入阻塞队列**，让其他线程能够进入临界区 。
            
        3. **唤醒后的重夺**：当被 `cv_signal` 唤醒从 `cv_wait` 返回时，该线程**会自动重新去获取并持有原来的互斥锁** 。
            
        4. **Mesa 语义（必须使用 while 循环重新检查条件）**：在 OS/161 的语义中，`cv_signal` 发出后，唤醒的线程不会立刻夺取 CPU 优先执行，它需要等发信号者释放锁后去重新排队竞争夺锁 。在这期间，刚才满足的条件可能会被另一个刚好冲进来的线程破坏。因此，**必须使用 `while` 循环重新检查唤醒条件，决不能用 `if`** 。
            

#### 💡 OS/161 条件变量解决有界缓冲区问题

C

```
int count = 0;
#define N 4
struct lock *l;
struct cv *full, *empty;

prod() {
    while(TRUE) {
        item = produce();
        lock_acquire(l);
        while (count == N) {       // 必须用 while，防止虚假唤醒或条件被抢占
            cv_wait(full, l);      // 原子释放锁 l 并阻塞在 full 条件变量上
        }
        insert_item(item);
        count++;
        cv_signal(empty, l);       // 唤醒可能在等待 empty 的消费者，但不释放锁
        lock_release(l);
    }
}

con() {
    while(TRUE) {
        lock_acquire(l);
        while (count == 0) {       // 检查边界
            cv_wait(empty, l);     // 释放锁并挂起
        }
        item = remove_item();
        count--;
        cv_signal(full, l);        // 唤醒因满而阻塞的生产者
        lock_release(l);
        consume(item);
    }
}
```

## 四、 经典并发难题二：哲学家就餐问题（Dining Philosophers）

### 1. 场景模型

- 5 位哲学家围坐在一张圆桌旁，进行“思考”和“就餐”的循环 。
    
- 桌上一共只有 5 把叉子，左右各一把，**每个人吃 spaghetti（意大利面）必须同时拿起左右两把叉子** 。
    

### 2. 错误非解决方案（为什么会导致死锁？）

如果每个人都贪婪地执行相同的逻辑：先拿左边叉子，再拿右边叉子 ：

C

```
void philosopher(int i) {
    while (TRUE) {
        think();
        take_fork(i);           // 拿左叉
        take_fork((i+1) % N);   // 拿右叉
        eat();
        ...
    }
}
```

- **死锁场景**：在极端的定时下，所有人同时拿起了左手边的叉子 。此时每个人手里都有一把叉子，并在无限期等待右边的人放下叉子，导致系统陷入**环路等待死锁** 。
    

### 3. 正确解决方案

课堂和讲义给出了两种代表性的解法：

#### 解法 A：大全局锁状态跃迁法（讲义给出的解法）

不把叉子当成实体锁，而是把哲学家的行为状态（`THINKING`, `HUNGRY`, `EATING`）保存在一个全局数组中，并用一个全局互斥锁 `mutex` 来保护状态的改变 。

- **核心思想**：只有当左右邻居都没有在吃，且自己处于饥饿状态时，才一举把自己的状态变更为 `EATING` 并通过信号量继续，否则在自己的专属信号量 `s[i]` 上阻塞 。放下叉子时，需要主动帮左右邻居进行 `test` 尝试唤醒 。
    

C

```
#define N 5
#define LEFT (i+N-1)%N
#define RIGHT (i+1)%N
int state[N]; 
semaphore s[N];     // 每个哲学家一个专用信号量，用于阻塞自己
semaphore mutex = 1;// 全局互斥锁

void take_forks(int i) {
    down(&mutex);
    state[i] = HUNGRY;
    test(i);        // 尝试一次性拿下两把叉子
    up(&mutex);
    down(&s[i]);    // 如果 test 没成功，会在这里阻塞；若成功，s[i]被up过，将直接通过
}

void put_forks(int i) {
    down(&mutex);
    state[i] = THINKING;
    test(LEFT);     // 吃完后，帮左邻居测试能否就餐
    test(RIGHT);    // 帮右邻居测试能否就餐
    up(&mutex);
}

void test(int i) {
    if (state[i] == HUNGRY && state[LEFT] != EATING && state[RIGHT] != EATING) {
        state[i] = EATING;
        up(&s[i]);  // 释放该哲学家的阻塞状态
    }
}
```

#### 解法 B：打破对称性——锁排序法（来自台下讨论）

- **核心思想**：死锁的根本原因在于依赖链形成了环 。可以通过为资源进行全局硬性编号（0 到 4），规定**任何哲学家必须先拿编号小的叉子，再拿编号大的叉子**（或者相反） 。
    
- **效果**：对于 0 到 3 号哲学家，由于左叉编号小于右叉，表现为先左后右 。但对于 4 号哲学家，他的周围是 4 号和 0 号叉子，按照规则，他必须**先拿 0 号（右手）再拿 4 号（左手）** 。这样，4 号哲学家和 0 号哲学家就会在 0 号叉子上直接展开竞争，环路依赖链被彻底切断，成功熔断死锁 。
    

## 五、 经典并发难题三：读者-写者问题（Readers and Writers Problem）

### 1. 场景模型

用于模拟对共享数据库（如机票订票系统）的访问控制 ：

- **多读者共享**：同一时刻可以允许多个读者同时读取数据库，它们之间不需要互斥，否则浪费并行性能 。
    
- **写者独占**：为了防止读写冲突和数据不一致，写者执行写入时，必须排斥所有的其他读者和写者，即拥有绝对的独占访问权 。
    

### 2. 信号量解决方案（第一类读者优先）

引入一个读者计数器 `rc` 来记录当前有多少读者在读或想要读 。

- 使用 `mutex` 来保护对计数器 `rc` 的原子修改 。
    
- 使用信号量 `db` 来控制对数据库整体的独占锁 。
    

C

```
semaphore mutex = 1; // 控制对 rc 的互斥访问
semaphore db = 1;    // 控制写者进入/读者集体进入数据库的独占锁
int rc = 0;          // 处于读状态的读者数量

void reader(void) {
    while (TRUE) {
        down(&mutex);
        rc = rc + 1;
        if (rc == 1) { 
            down(&db);   // 如果我是进来的第一个读者，负责代表全体读者把写者锁在外面
        }
        up(&mutex);
        
        read_data_base(); // 多个读者可同时在此处并发行走
        
        down(&mutex);
        rc = rc - 1;
        if (rc == 0) {
            up(&db);     // 如果我是离开的最后一个读者，负责代表全体读者释放数据库独占锁
        }
        up(&mutex);
        
        use_data_read();
    }
}

void writer(void) {
    while (TRUE) {
        think_up_data();
        down(&db);       // 获取绝对独占访问权，若有读者或写者在内部则在此阻塞
        write_data_base();
        up(&db);         // 释放独占权
    }
}
```

### 3. 工程批判与反思（读写锁的“坏味道”）

课堂上特别提到了多位研究人员对读写锁（Reader-Writer Lock）的工程批判 ：

- **写者饥饿问题**：如果读者源源不断地进来，`rc` 永远不会降到 0，写者将被无限期无限推迟，造成严重的写者饥饿 。
    
- **退化现象**：如果写操作本身发生得非常频繁，该锁就会频繁发生激烈竞争，在实际表现上退化成一个普通的互斥锁，且带来了更多的开销 。
    
- **工程建议**：过度drift（倾向）使用读写锁通常暗示着程序员还没很好地理解系统架构。除非确信读的比例占据压倒性优势，否则在现代高并发设计中，更倾向于使用多副本发布、Copy-On-Write 或无锁并发进程来保护只读图片（快照）数据 。
