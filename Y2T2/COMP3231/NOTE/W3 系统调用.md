
## 💻 操作系统：系统调用接口与实现机制

## 模块一：系统调用接口（高层视角）

### 1. 计算机系统的基本结构

- **模式隔离**：系统通过硬性边界将运行环境划分为**用户模式（User Mode）**与**内核模式（Kernel Mode）** 。
    
- **位置与开销**：应用程序及系统库位于用户级内存中，主要占据绝大部分内存空间；而操作系统内核、核心设备及特权结构则在内核级运行，属于系统的固定开销 。
    
- **跨越边界**：应用程序若想走出“用户盒子的限制”与外部环境（如硬件设备、网络、文件）进行交互，必须通过系统调用（System Calls）安全地跨越这一黑白分明的边界 。
    

### 2. 系统调用的核心定义与特性

- **特权安全门**：系统调用可被视为一种特殊的、行为受严格限制的函数调用 。其核心目的在于提供一个进入内核的**受控入口（Controlled Entry）** 。
    
- **原子级别特权提升**：触发系统调用的瞬时，硬件会同步激活特权模式（Privileged Mode）并转移控制权 。
    
- **拒绝任意执行**：不允许用户级应用程序跳过安全检查直接跳转进内核 binary 的任意点执行 ，必须强制从固定的、安全的、受控的常规基准位置开始运行 。
    

### 3. Unix 经典进程与文件管理系统调用

为了后续深入分析实现，需要熟记以下经典系统调用的功能约定：

|**系统调用**|**描述**|
|---|---|
|`pid = fork()`|**一分为二**：复制当前进程创建一个一模一样的子进程。父进程返回子进程 PID，子进程返回 0 。|
|`pid = waitpid(...)` / `wait()`|**等待结束**：父进程阻塞挂起，等待子进程执行或终止完成 。|
|`execve(name, argv, envp)`|**核心映像替换**：用全新的程序及其上下文完全覆盖、替换当前正在运行的程序 image 。|
|`exit(status)`|**进程终止**：放弃控制权，直接退出当前进程并返回状态码给父进程 。|
|`open()` / `close()`|文件的打开与关闭 。|
|`read()` / `write()`|从文件读取数据到缓冲区，或将缓冲区数据写入文件 。|
|`lseek()`|移动文件内部的读写指针，实现快进或跳转 。|
|`stat()`|获取文件的状态及统计信息（Statistics） 。|

> 💡 **对比 Win32 API 差异**：Unix 的 `fork` 与 `execve` 在 Windows 中对应的功能被整合为了一个单一的系统调用 `CreateProcess` 。此外，Win32 原生并不直接支持 Unix 风格的 `link`、`mount`、信号（如 `kill`）以及部分权限安全保护机制（如 `chmod`） 。

## 模块二：硬件支撑 —— MIPS R3000 架构精要

由于硬件不可能自行实现复杂的业务逻辑，其设计指导原则是**做最少的工作（Do the Minimum）**，然后迅速委托给操作系统软件处理 。

### 1. 特权模式与“不安全指令”防御

- **CPU 运行状态**：CPU 内部通常有特定状态位或寄存器表明当前的执行权限 。
    
    - **用户模式**：仅被允许执行面向用户的“安全”指令子集 ，仅能直接影响应用自身的普通硬件状态 。
        
    - **特权模式**：可以访问所有指令、寄存器和全部内存空间 。
        
- **实例 exploit 场景**：x86 下的 `cli`（清除中断标志）属于典型的特权指令 。如果允许用户级程序随意运行 `cli` 然后进入 `while(true)` 死循环，由于中断被断绝，CPU 将被永远卡死 。因此必须在硬件层面彻底封锁非特权模式下的此类指令 。
    

### 2. 控制协处理器 0（Coprocessor 0, CP0）

MIPS 将系统控制和异常管理功能剥离、挂载到了一个专门的附属结构中，即 **CP0（控制协处理器）** 。

- **操作指令**：非特权模式完全不可见 。内核模式下通过专用指令来操控：
    
    - `mfc0 register, cp0_reg`：Move **From** Coprocessor 0（将 CP0 寄存器的值移入通用寄存器） 。
        
    - `mtc0 register, cp0_reg`：Move **To** Coprocessor 0（将通用寄存器的内容写入 CP0 寄存器配置项） 。
        

### 3. CP0 核心状态寄存器组

|**CP0 寄存器**|**功能详解**|
|---|---|
|**`c0_status`**<br><br>  <br><br>(状态寄存器)|存放 CPU 的关键状态控制位，重点包括 ：<br><br>  <br><br>• **`KU` (Kernel/User)**：`0` 代表当前处于内核模式，`1` 代表用户模式 。<br><br>  <br><br>• **`IE` (Interrupt Enable)**：全局中断总开关，`0` 屏蔽所有中断，`1` 开启 。<br><br>  <br><br>• **三级硬件状态栈**：分为 **`c` (Current 当前)**、**`p` (Previous 先前)**、**`o` (Old 过去)** 三组快照副本（如 `KUc, IEc` 等） 。当异常发生时，硬件自动将当前状态位左移压栈入先前状态，防止状态丢失 。|
|**`c0_cause`**<br><br>  <br><br>(原因寄存器)|存储最近一次引发系统进入操作系统的具体原因 。<br><br>  <br><br>• **`ExcCode` (异常码位)**：用 5 个 bits 区分基本异常类型 。<br><br>  <br><br>- `0 (Int)`：外部硬件中断（如定时器） 。<br><br>  <br><br>- `2 / 3 (TLBL / TLBS)`：快表物理翻译缺失或失效 。<br><br>  <br><br>- `8 (Syscall)`：用户 unconditional 触发了 `syscall` 指令 。<br><br>  <br><br>• **`BD` (Branch Delay 标志位)**：若引发异常的指令正好处于**分支延迟槽**内，则置该位 。|
|**`c0_epc`**<br><br>  <br><br>(异常程序计数器)|保存并锁定发生异常时的 Program Counter（程序计数器） 。在操作系统处理完 fault 并返回时，作为**精准恢复执行**的目标地址 。|
|**`c0_badvaddr`**|当发生段错误、虚拟内存翻译失效（Page Fault）等致命或非致命地址异常时，记录当时程序试图读写的**非法虚拟地址** 。|

### 4. 异常向量表（Exception Vectors）

当异常暴发，硬件会强行将程序计数器（PC）重定向到硬编码的固定物理/虚拟地址 。MIPS 进行了高度精简集中 ：

- **`0x80000000`**：仅用于处理 `kuseg` 区域的用户态 TLB 缺失 。
    
- **`0x80000080`**：**通用异常向量入口**。包括系统调用（Syscall）、外部设备中断等其他所有异常，一律在此处切入内核 。操作系统需要在此固定的微小空间内放置一段跳转汇编，先查明成因，再进行扇出分发 。
    

## 模块三：软硬件协同 —— 异常与转换全流程

### 1. 硬件切入内核的底层动作（以中断/系统调用为例）

假设用户程序正在地址 `0x12345678` 顺利执行，下一周期的瞬时发生了中断或发起了系统调用 ：

1. **快照保存**：硬件自动将当前的 PC 值（`0x12345678`）强制锁存进 CP0 的 `c0_epc` 寄存器中 。
    
2. **状态压栈**：状态寄存器位发生链式平移（`Current -> Previous -> Old`） 。
    
3. **特权强制卡位**：硬件强制将当前特权级 `KUc` 归零（**进入内核态**），同时将全局中断 `IEc` 归零（**紧急关闭中断**，避免内核陷入无休止的嵌套打断） 。
    
4. **填入原因**：把对应的异常识别码（中断为 `0`，系统调用为 `8`）填进 `c0_cause` 的 `ExcCode` 。
    
5. **PC 闪现**：将程序计数器 PC 强行篡改为通用异常处理地址 `0x80000080` 。硬件动作结束，软件（操作系统汇编）接管 。
    

### 2. 软件从内核安全返回的动作

在软件完成全部事务准备退出内核时，必须执行一段固定的“魔法汇编序列” ：

1. **装载 EPC**：将保存在内存或 TCB 里的原 EPC 地址取出，暂存到专为内核保留的通用寄存器 `k1` 中 。
    
2. **跳转返回**：执行指令 `jr k1`（跳转到保存的指令处） 。
    
3. **延迟槽原子级回滚**：由于 MIPS 具有分支延迟槽特性，在执行 `jr k1` 的同时，紧随其后的**延迟槽指令**必须安排为 `rfe`（Restore from Exception，从异常恢复） 。
    
4. **效果**：`rfe` 指令促使 CP0 状态寄存器位发生反向移位回滚（`Old -> Previous -> Current`） 。`KU` 和 `IE` 回复为原先的用户态快照（通常为 `1` 和 `1`），系统无缝回到用户空间 。
    

## 模块四：个案深度拆解 —— OS/161 系统调用全生命周期

以用户级调用 `int read(int fd, void *buf, size_t nbytes)` 为切入点 ，全面拆解其内部的 11 个软硬件协作步骤 。

### 1. 传递约定的确立（OS/161 规范）

系统调用与普通的 C 函数调用共享了一套高度相近的寄存器传递规约 ：

- **输入参数**：前 4 个参数无缝存放于 `a0, a1, a2, a3` 寄存器 。
    
- **系统调用标识**：由于参数占满了 `a0-a3`，额外引入 **`v0` 寄存器存放系统调用号**（`read` 的系统调用号为 `5`） 。
    
- **输出状态机（双寄存器返回机制）**：
    
    - 返回时，**`a3` 充当状态标志**：若 `a3 == 0` 代表大获成功，此时 `v0` 存储实际读取到的字节数 ；若 `a3 != 0` 代表发生故障，此时 `v0` 内塞入标准的内核错误码（`errno`） 。
        
    - 内核还假定，整个过程中用户态的局部核心寄存器（`s0-s8, sp, gp, ra`）必须由内核软件完全保护并原样归还 。
        

### 2. 用户态的前半生（`libc` 库的适配）

当用户调用 `read(fd, &buf, 1024)` 时 ，编译器与系统库协同完成以下动作：

1. **参数入库**：代码将 `fd` 挪入 `a0`，缓冲区指针挪入 `a1`，并利用延迟槽将常数 `1024` 写入 `a2` 。
    
2. **跳转通用桩**：使用 `jal read` 指令跳入封装好的库函数 。
    
3. **加载识别号**：在库函数内部，首先把 `read` 的身份码 `5` 装入 `v0` 。然后通过一个尾调用跳转 `j __syscall` 冲向统一的系统调用爆发点 。
    
4. **爆发**：在 `__syscall` 内部，执行字面意思上的 **`syscall` 硬件指令** 。这一瞬间，硬件依照模块三的步骤，斩断用户态执行，瞬间将系统强制打入特权内核态，PC 锚定到 `0x80000080` 。
    

### 3. 内核态的惊心动魄（汇编至 C 的桥梁）

一旦跨入内核，汇编级服务例程必须以最快速度在**没有任何可用栈**且不破坏用户寄存器的严苛环境下搭建好 C 语言环境 ：

代码段

```
exception:
    move k1, sp                  # 1. 紧急避险：将用户态栈指针 SP 藏入留守寄存器 k1
    mfc0 k0, c0_status           # 2. 捞取状态：检查 KUc 位，看刚才是否来自用户态
    andi k0, k0, CST_KUp
    beq  k0, $0, 1f              # 3. 若本身就在内核（嵌套异常），则保留原样跳过栈切换
    nop                          # 延迟槽
    la   k0, curkstack           # 4. 从全局变量 current_kstack 加载预设好的内核栈指针
    lw   sp, 0(k0)               # 5. 替换完毕：此时 SP 彻底脱离用户控制，指向安全的内核空间
    nop                          # 延迟槽
1:
    mfc0 k0, c0_cause            # 6. 获取 ExcCode
    j    common_exception        # 7. 飞奔汇编主战场
    nop
```

进入 `common_exception` 后，软件开始为 C 语言函数打造其第一级参数——**陷阱帧（Trap Frame）** ：

1. **栈空间开辟**：执行 `addi sp, sp, -164`，一次性在内核栈上抠出 37 个字长的完整结构体空间 。
    
2. **疯狂快照**：连续执行 `sw` 指令，把用户态原封不动的 32 个通用寄存器（包括刚才暂存的真实用户 `sp`、`ra`、`v0` 等）以及 CP0 的 `c0_epc, c0_status, c0_badvaddr` 按照规范的结构体顺序**悉数倾倒、铺满内核栈** 。
    
3. **完成接轨**：执行 `addiu a0, sp, 16`，将这块刚刚在栈上乱序/顺序码好的结构体首地址作为第一个参数（a0）传递 。
    
4. **杀入 C 逻辑**：调用 `jal mips_trap` 。在 C 语言层面，该参数被自然而然地解析为 `struct trapframe *tf` 指针 。
    

C 

```
void mips_trap(struct trapframe *tf) {
    // 静态断言：严密检查 C 语言对结构体尺寸的定义是否与前面汇编手工数出来的 37*4 字节完美契合
    assert(sizeof(struct trapframe) == (37 * 4)); 
    // 提取系统调用号 tf->tf_v0，进入大型 switch-case 扇出分发
    // 在这里最终引发真正的内部 read() 或驱动层数据拷贝
}
```

### 4. 凯旋与适配（用户态的后半生）

当内核代码处理完毕、`mips_trap` 函数退出后，控制权落回 `exception_return` 汇编标签 。

1. 汇编代码完美倒序执行 `lw` 弹出指令，将陷阱帧（可能已被内核改写了 `v0` 和 `a3`）中的数据原样灌回物理寄存器 。
    
2. 最后一级栈指针加载，执行 `jr k0` 加延迟槽 `rfe` 闪回用户态 。
    

此时回到用户态 `__syscall` 的下一行指令处 ：

代码段

```
    beqz a3, 40065c <_syscall+0x1c>   # 1. 检验状态位：如果 a3 是 0（代表大获成功），直接带上 v0 的字节数跳往正常退出点
    nop                               # 延迟槽
    lui  at, 0x1000                   # 2. 如果发生不测（a3 != 0），内核已把错误号留在了 v0 里
    sw   v0, 0(at)                    # 3. 系统库手动将该错误码转移，塞入全局 errno 变量中
    li   v1, -1                       # 4. 强行将 v1 和 v0 都用补码重写为 -1
    li   v0, -1                       # 5. 此时 read() 函数的正式 C 语言返回值被牢牢锁死为 -1
40065c:
    jr   ra                           # 6. 顺理成章弹回用户写下的原生代码调用处
    nop
```

通过这一套天衣无缝的适配层，一个跨越特权隔离鸿沟的底层系统操作，在 C 程序员眼里，就变成了一个普通的、只管返回 `-1` 或成功字节数的常规函数 。
