=== Question A4 === [12 marks]

Organisations are shifting from AI assistants that support human decision-making to autonomous AI agents that independently execute and approve tasks. These tasks include document reviews, code reviews, automated simulations and analysis. In some of these cases, the human reviewer step has been removed to increase efficiency and remove labour costs.

You are a government agency asked to provide insight into this issue and asked to name 3 recommendations to do this securely and effectively. [6 marks]

Recommendation 1 (guide: 2-3 sentences):

Mandatory Human-in-the-Loop Approval Gates for Consequential Actions. Organisations should define clear risk thresholds above which an autonomous AI agent must pause and obtain explicit human authorisation before executing. This preserves efficiency for routine low-risk tasks while preventing the agent from autonomously taking irreversible actions (deploying code, approving contracts, making legal determinations) that may contain undetected errors, hallucinations, or adversarial prompt injections.


Recommendation 2 (guide: 2-3 sentences):

Principle of Least Privilege for AI Agent Permissions and Capability Boundaries. Each agent should be granted only the minimum set of permissions, data-access rights, and tool integrations necessary to complete its designated task, with no ability to self-escalate or invoke other agents without explicit authorisation. This limits blast radius if an agent is compromised or manipulated, and prevents lateral movement across organisational systems through a single compromised agent.


Recommendation 3 (guide: 2-3 sentences):

Tamper-Proof Audit Logging and Continuous Behavioural Monitoring. Every action, input, decision, and output produced by an autonomous AI agent must be logged in a tamper-evident, time-stamped format and regularly reviewed by both automated anomaly detection and human overseers. This ensures that organisations can reconstruct the full decision chain of any agent action for incident response, legal accountability, and regulatory compliance - and can detect systematic errors or adversarial manipulation before they cause significant harm.


If one idea was to become mandatory for all Australian companies, which one would it be and why [6 marks] (guide: 3-4 sentences)?

Recommendation 3 - Tamper-Proof Audit Logging - should be the mandatory baseline. Without comprehensive audit trails, no other security control can be effectively verified: companies cannot prove their AI agents behaved correctly, regulators cannot audit compliance, and incident responders cannot determine what went wrong after a failure. Unlike human-in-the-loop requirements (which may be impractical for high-throughput applications) or least-privilege configurations (which require complex, bespoke per-agent setup), audit logging is universally implementable across all AI agent architectures with minimal operational overhead. It also aligns with existing Australian legal obligations under the Privacy Act 1988 and the Security of Critical Infrastructure (SOCI) Act, creating a foundation for enforceable accountability without requiring entirely new regulatory frameworks.

Later in the day, you realize that there is a large amount of outcoming traffic from the network and realize that it is from the same employee. What are the top steps and recommendations, immediately and in the long term, provide a brief explanation as you do this. Is legal action required?

1. Steps and Recommendations [6 marks]

1.1. Immediate:
1.1.1. Immediately revoke or block the employee's network access and credentials to contain the active data exfiltration. Isolate the endpoint from the network to halt any further outbound transfer while preserving the system state.
1.1.2. Preserve and secure all relevant digital evidence without alteration - capture packet captures, SIEM logs, authentication records, and file access logs. Following Locard's Exchange Principle, every digital action leaves a trace; this forensic chain of custody is critical for any subsequent investigation or legal action.
1.1.3. Escalate immediately to the Security Incident Response Team (SIRT), HR, and Legal/Management. Document the full incident timeline, including the earlier suspicious source code access that was initially ignored, to establish a complete picture for investigation.

1.2. Long-term:
1.2.1. Enforce strict Role-Based Access Control (RBAC) aligned with the Principle of Least Privilege and the Bell-LaPadula No Read Up property. A Sales employee has no legitimate business need to access source code repositories; access should be restricted by role so that such anomalous access is technically impossible rather than merely flagged.
1.2.2. Deploy Data Loss Prevention (DLP) tools and network egress monitoring with automated alerts on large-volume outbound transfers, particularly to unusual destinations. Integrate these signals into a SIEM with AI-assisted anomaly detection so the SOC can catch exfiltration patterns in real time rather than reactively.
1.2.3. Establish and regularly rehearse a formal Incident Response Playbook that mandates escalation of any anomalous insider access event, however seemingly benign. Adopt a Zero Trust posture ("Never Trust, Always Verify") and conduct periodic access reviews so that privilege creep is detected before it can be exploited.

2. Should you have done anything differently other than ignoring the first suspicious activity? Why? [4 marks] [guide: 2-3 sentences]

Yes - the first incident should have been escalated immediately rather than dismissed as curiosity. A Sales employee accessing large volumes of source code is a clear violation of the Principle of Least Privilege and represents a textbook insider threat indicator; ignoring it was a Type II error (false negative) that allowed the threat to escalate into confirmed data exfiltration. Zero Trust architecture demands that anomalous access be verified explicitly regardless of whether the actor is an internal employee, and a low-cost investigation at that point would have prevented the far more costly breach that followed.

Legal action is likely required. Beyond legal compliance, the company should notify affected internal stakeholders (e.g., product teams whose source code was stolen) and conduct a root-cause analysis to remediate the access control failures that enabled the breach. Finally, the company should review whether the stolen source code poses a competitive intelligence risk and take steps such as accelerating security patching of the exposed product to reduce downstream harm.

=== Question B4 === [18 marks]

Suppose you are tasked with revising the design of a "nuclear football" which could be used to launch a nuclear strike. Currently, it is protected by a 8-digit PIN which must be entered correctly before the football opens. Once successfully activated the launch order is transmitted from the football using shortwave radio. The launch order is a 1024-bit secret number.

A security engineer has suggested adding a biometric sensor for multi-factor authentication. To activate the football, a 1 Megabyte photo of your face is taken and hashed using a proprietary facial hashing algorithm to produce a 30-bit "facehash".

You must also enter the 8-digit pin, which is XOR-ed with the facehash. The result is then sent to an internal authentication unit to verify it matches, and decide whether or not to activate the football.

Approximately how many bits of work would an attacker need to do to activate the football, assuming they could take physical ownership of the football? Explain your thought processes as you go.

a) How many bits of work in the worst case (8 marks)?

Bits of work: 27 bits (approximately 10^8 operations)

Thought Processes / Working

Step 1 - Analyse PIN entropy:
  8 decimal digits, each 0-9 => 10^8 = 100,000,000 possible PINs.
  Bits: log2(10^8) = 8 * log2(10) ~= 8 * 3.32 = 26.57 => approximately 27 bits.

Step 2 - Analyse facehash:
  1 MB photo hashed to 30 bits => 2^30 ~= 10^9 possible facehash values.
  30 bits > 27 bits, so the facehash space is LARGER than the PIN space.
  Note: this "proprietary" algorithm is security through obscurity (violates Kerckhoffs's
  principle) and we cannot trust it to add security we cannot verify.

Step 3 - Critical XOR weakness (why MFA fails here):
  The system computes: (PIN XOR facehash) and checks against a stored value.
  XOR does NOT multiply security. An attacker with physical ownership can:
    1. Present their own face once => yields a fixed, known facehash F.
    2. The problem then reduces to: find PIN such that (PIN XOR F) == stored_value.
    3. Brute-force all 10^8 PIN values with their face held constant.
  The biometric factor becomes a constant offset and provides no additional protection.
  This defeats the purpose of multi-factor authentication entirely: the attacker only
  needs to search the smaller of the two spaces (PIN: 2^27 < facehash: 2^30).

Step 4 - Worst case:
  The attacker must try all 10^8 PINs before the last one succeeds.
  Worst case bits of work = log2(10^8) ~= 27 bits.

Additional weaknesses not affecting this calculation but worth noting:
  - 30-bit hash is too small: birthday collision in 2^15 = ~32,000 attempts.
  - The 1024-bit launch order is transmitted over unencrypted shortwave radio,
    meaning any eavesdropper with a receiver can capture it. This bypasses the
    authentication entirely if the signal can be replayed or observed.

b) How long would it take for a government intelligence agency to brute force the password in the worst case (10 marks)? List any assumptions you have.

Time (years in nearest power of 2): 2^(-38)

Assumptions / Thought Processes / Working

Assumptions:
  1. Physical ownership => government engineers extract the internal authentication unit
     and test PINs electronically, fully bypassing any physical rate limiting.
  2. A major intelligence agency (e.g. NSA/GCHQ) can dedicate specialised ASIC/FPGA
     hardware to this task. Conservative estimate: 2^40 PIN verifications per second
     (approximately 10^12/s, achievable with a modest cluster of modern ASICs).
  3. 1 year ~= 3.15 * 10^7 seconds ~= 2^25 seconds.
  4. Worst case = all 2^27 PINs must be tried (correct PIN is the last one checked).

Calculation:
  Work required:  2^27 PIN attempts
  Rate:           2^40 per second
  Time in seconds: 2^27 / 2^40 = 2^(27-40) = 2^(-13) seconds (~= 0.1 microseconds)
  Time in years:  2^(-13) seconds / 2^25 seconds/year = 2^(-38) years

Result: 2^(-38) years -- effectively instantaneous (less than 1 microsecond).

Even with a far more conservative single consumer GPU (~10^9 = 2^30 per second):
  Time = 2^27 / 2^30 = 2^(-3) seconds ~= 0.125 seconds
  Years = 2^(-3) / 2^25 = 2^(-28) years

In both cases this system is broken in well under one second. A government agency
with dedicated hardware would crack it in nanoseconds. The root cause is that the
8-digit PIN provides only ~27 bits of effective security, which is far below the
minimum recommended ~80-128 bits for any security-critical system. XOR combining
the PIN with a facehash adds no additional security because the attacker can fix
the biometric factor and reduce the problem to a single-factor PIN brute force.

=== Question B5 === [18 marks]

A politician, after reading PKI X.509 Certificate formats believes that the best approach to running the government is to be the sole root authority themselves. The politician permits the ones they trust closest to because Intermediate Authorities which then permits access to each object. The Intermediate Authorities then go out and seek out respective permitted individuals.

Is this an effective system? What are different issues which may occur here? [12 marks]

This system is not effective. While it mirrors the hierarchical PKI trust model (Root CA -> Intermediate CA -> End-entity), applying it to government governance introduces severe structural problems:

1. Single Point of Failure / Catastrophic Centralisation: The politician acting as sole Root CA means the entire system's integrity depends on one person. If the politician is compromised (coerced, corrupted, or removed from office), every trust relationship in the system collapses immediately. Real PKI distributes root trust across many independent root CAs precisely to avoid this.

2. Unchecked Concentration of Power: The Root CA can unilaterally grant or revoke any Intermediate Authority's trust at any time with no oversight. This gives the politician absolute, unchecked control over who can access what in government — equivalent to a dictatorship with no separation of powers. The politician can revoke political opponents' access or silently grant allies elevated privileges.

3. Transitivity of Corrupted Trust (Intermediate CA Compromise): If an Intermediate Authority is corrupted or compromised, they can issue access grants to anyone they choose within their scope. The politician (Root CA) may not detect this. A single bad Intermediate Actor propagates illegitimate trust throughout their entire sub-chain.

4. Scalability Bottleneck: A single root authority cannot personally evaluate every trust decision as government grows. The system must rely entirely on Intermediate Authorities whose judgment and integrity cannot be verified — the root has already delegated without technical constraints.

5. No Revocation Infrastructure / CRL Problem: X.509 PKI requires Certificate Revocation Lists (CRLs) or OCSP. In this political model, revoking an Intermediate Authority's trust requires the politician to act. If the politician is unavailable, incapacitated, or unwilling, compromised intermediaries cannot be removed, leaving the system exposed indefinitely.

6. Conflict of Interest: The politician simultaneously controls who gets access and benefits politically from that control. Unlike commercial PKI where Root CAs are audited by independent bodies (e.g., WebTrust), there is no independent auditor or Certificate Transparency log to detect abuse.

7. No Checks and Balances: Democratic governments operate on separation of powers. This system vests judicial, legislative, and executive trust decisions in one person, violating the foundational principle that no single entity should hold unchecked authority.

8. Key/Credential Compromise at the Root: If the politician's root signing key or authority is compromised through social engineering, coercion, or insider attack, there is no higher authority to detect or correct this — the entire trust hierarchy is silently poisoned from the top.

What policies would have to be defined to ensure that least privilege is maintained? [6 marks]

To enforce least privilege in this PKI-style government trust model:

1. Name Constraints and Scope Limitation: Each Intermediate Authority must be issued with explicit name constraints restricting them to granting access only within their designated domain (e.g., a defence intermediate authority can only issue access grants for defence-related resources, not health or finance). This is an X.509 Name Constraints extension applied as policy.

2. Path Length Constraints: Intermediate Authorities must not be permitted to create further sub-authorities (path length = 0). This prevents uncontrolled delegation chains where access rights silently multiply beyond intended scope.

3. Minimum Necessary Scope per Certificate: Every access grant issued by an Intermediate Authority must specify exactly which resources are accessible and at what level. Grants must never default to broad/wildcard access — each grant is scoped to the specific task or role.

4. Limited Validity Periods with Mandatory Renewal: All access grants must expire after a defined period and require active renewal. This forces regular review of whether access is still justified, preventing accumulation of stale privileges.

5. Mandatory Audit Logging and Certificate Transparency: All trust grants and revocations must be recorded in an immutable, independently audited transparency log. This allows external auditors to detect over-privileged grants or suspicious patterns — equivalent to CT logs in real PKI.

6. Independent Revocation Authority: Revocation capability must not rest solely with the politician. A separate independent body (e.g., an oversight committee) must have authority to revoke Intermediate Authority trust, ensuring compromised or corrupt intermediaries can be removed even if the root is unwilling to act.
